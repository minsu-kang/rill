# @rill/desktop

The React renderer of the Rill desktop app, built so that every screen can be looked at in Storybook without starting the app, the engine, a network or a model key.

The screens take their data as props or read it through a small `EngineClient` interface (`request` and `onEvent`). The stories and the tests give them a fake client that answers from fixtures. The Electron shell that wraps them (main process, engine process, secrets, tray, installer) is described in [The desktop app](#the-desktop-app). The window shows the app screen in `src/app/`, which wires the screens to the host API and the engine client, as described in [The window](#the-window).

## What is here

| Screen | Files | What it shows |
| --- | --- | --- |
| Workflow graph | `src/graph/` | A read-only React Flow canvas with a dagre layout from left to right (above 80 nodes or 240 edges it switches to a plain layered grid, because dagre takes seconds on such graphs). Each node card shows its status as an icon plus a word, the attempt count, a retry mark, and badges for external transfer, file writes and network calls. Click or Enter selects a node. |
| Inspector | `src/inspector/` | The settings of the selected node and every attempt of its last run: input, output, error and times. `JsonView` caps depth, rows and string length, so a large value cannot freeze the page. |
| Run history | `src/runs/` | The runs of a workflow with a status, a relative time, a dry-run tag and the start of the error. Picking a run draws its states on the graph. |
| Workspace | `src/workspace/` | The three screens together as in the design: graph in the middle, inspector on the right, history below. Live events from the client change the node cards as they arrive. |
| Failure explanation | `src/explain/` | The "why did it fail" flow for a failed run: a notice of what is sent to the model provider, an effort choice, the explanation card with the likely cause, signal chips, action buttons and an optional fix proposal handed to the chat box as a draft. |
| Agents, Rules and Hooks | `src/app/agents/`, `src/chat/AgentPicker.tsx` | The Agents tab with its sub-navigation: the Agents screen (a list, an editor, an import review), the Rules screen, the Hooks screen (a list, a form and an activity list), and the agent picker in the chat header. See [Agents](#agents), [The Rules screen](#the-rules-screen) and [The Hooks screen](#the-hooks-screen). |
| Recipe gallery | `src/recipes/` | The eight ready-made recipes with search and tag filter, a form built from each recipe's params, a draft preview with the graph, side-effect lines and the "external transfer" line, and a deploy button. |
| Chat panel | `src/chat/` | The right pane: chat tabs, each a conversation with the planner (questions, workflow preview, unsupported), an effort control, file attachments, flag confirmation before deploy, a model picker, an agent picker and a notes screen. See the next section. |
| App shell | `src/app/` | The top bar, the page container, the Workflows, Recipes, Agents and Settings screens and the chat aside, wired to the host API and the engine client. See [The window](#the-window). |
| Shared pieces | `src/ui/`, `src/theme/`, `src/i18n/` | Status chip and icons, color tokens for light and dark, and a typed Korean and English dictionary. |

Run state lives in `src/model/` as pure functions: `statesFromSteps` for a finished run, `reduceEvent` for the live event stream, `displayState` for what a card shows. A trigger writes no step row, so a trigger of an open run is shown as succeeded.

## The chat panel

`src/chat/ChatPanel.tsx` is the whole right pane as one component that takes its world as props:

| Prop | Meaning |
| --- | --- |
| `client` | An `EngineClient`. The panel calls `plan`, `cancelPlan`, `deployPlan`, `llmModels` and `listMemory`, and never subscribes to events. |
| `port` | An `AttachmentPort`, see below. |
| `catalog` | The node list (`nodeCatalog`) used to title the cards of the preview and the flag groups. |
| `hints` | Optional measured cost and delay per effort step, `{ effort, costUsd?, latencyMs?, basis }`. Without it nothing is shown next to the steps: the numbers must come from evaluation runs, never from this package. |
| `editContext` | Optional `{ workflowId, nodeId? }`. When given, every `plan` request carries `workflowId` and `selection`, which puts the planner in patch mode. |
| `newId` | Optional plan id generator, for tests and stories. The default is `crypto.randomUUID`. |
| `onDeployed`, `onSelectModel`, `onClearEditContext` | Callbacks. The panel does none of these things itself. |
| `initialEntries`, `initialDraft` | Optional starting conversation and draft text for the first chat tab, for stories and tests. |

The conversation lives only in component state: a pure reducer (`src/chat/model/conversation.ts`) holds the entries, the draft, the attachments, the effort and the memory switch. Nothing is written to disk, `localStorage` or `sessionStorage`. The provider side is stateless, so each `plan` request carries the whole history as `turns` (at most 40, the engine's limit); when a conversation reaches the limit the panel offers to open a new chat tab. A new tab starts with the defaults.

What the person sees and decides:

- Composer layout, top to bottom: the text area; one toolbar row with Attach files and the effort control on the left and Send on the right (when the panel is narrower than about 470px the effort control moves to a second line); a small Options line that is closed by default and holds the notes switch and the advanced effort step (when notes exist but are switched off, the closed line says "Notes off" beside the button; the advanced step shows itself in the effort control); and one muted footer with the transfer notice and the shortcut hint. The transfer notice never needs a click to be seen. It is one quiet line with a small arrow icon: "Sent to the AI provider" when only the request goes out, and the list on screen ("Sent to the AI provider: your request, attached files, notes, agent settings") as soon as files, notes or agent settings are included. The tooltip always holds the full list. There is no coloured pill any more: the attached-file chips carry no badge, the graph shows a small arrow icon (with the full label as hidden text and the hint as tooltip) on a step that sends content out, the recipe cards show the arrow with a muted "External transfer" label, and the first-run card explains once what leaves the computer. The coloured badge stays where it explains in detail: the Model settings and the dry-run dialog.
- Effort steps: fast `low`, normal `medium` (default), careful `high`, very careful `xhigh`, and `max` under an advanced toggle. A step the active model does not list in `capabilities.effortLevels` is disabled with the reason. The answer shows requested and effective effort when the engine lowered it, and the cost as an upper bound (`null` shows "unknown").
- Send is Ctrl+Enter or Cmd+Enter. Plain Enter is a line break, so a multi-line draft is safe to write. It is never sent while a plan runs, while a file is being added, with an empty draft, with more than 8000 characters or without a model.
- Questions: a default that is one of the options is preselected and counts as an answer. A question with no options is a free text field that starts empty; the model default is shown beside it as a suggestion that the person accepts with a click or types over. A default that is not one of the options is ignored. The planner also treats an unchanged default as model text, never as text the person wrote. Answers travel as the `answers` of a user turn, never as part of the request text, because the planner treats a chosen option differently from text the person wrote.
- Flags: each flag of a plan has its own checkbox, grouped by node. Deploy stays disabled until the confirmed keys equal the flag keys of the plan (`flagKey` from `@rill/protocol`); the engine requires the same.
- Every place that sends something to the model provider says so: the composer notice (request, attached files, notes, agent settings), the badge on each attached file, the model picker (`dataNote`) and the notes screen.
- A plan that is running can be cancelled and the draft and attachments come back. When the engine has answered `cancelPlan` (or failed to) and the plan request has still not settled, the panel leaves the planning state itself and ignores a late answer for that plan. Closing the panel, or closing the chat tab, while a plan runs sends `cancelPlan` and drops the answer.
- Only the newest workflow card can be deployed. An earlier one says that a newer plan replaced it, and its flag boxes and Deploy button are off. While a new plan is being made, every Deploy button is off.
- **A second opinion on a plan.** Below the Deploy row (and its error) a workflow card has a part for the reviewer (`ReviewPart` and `ReviewPanel` in `src/chat/`, state in `src/chat/model/review.ts`, the engine's `reviewPlan`). It lists the agents of the kind Reviewer: a select when there are several, none when there is one, and with none the button is off and the hint says to create one on the Agents tab (while the agents load or fail to load it says that instead). The button is off for a deployed plan too, with a reason; a result that was already shown stays. Before it is pressed, a quiet line with the arrow icon sits next to the button: "Sends the plan and your request to the AI provider", or "Sends the plan, your request and the settings of this reviewer to the AI provider" when the picked reviewer has a persona, instructions or at least one skill (`hasAgentText` in `src/engine/agents.ts`), because the engine puts that agent block in the system prompt of every review. The request is `{ planId, agentId }` and nothing else (the effort stays at the engine's default). While it runs the part says "Asking the reviewer…" with Cancel; the engine has no call to stop a review, so Cancel, like Close on a failure explanation, only stops waiting and drops the answer, and says so. The result is a panel on the card: the advice-only line, the summary, the findings in the order the engine gave them (it already sorts them problem, warning, info) each with a chip that carries a word, the node id as plain text when there is one, then the meta line (reviewer, provider and model, the cost, the number of skills, a left-out note and the cost note) and "The plan and your request were sent to the AI provider." (with "the settings of the reviewer" added when the reviewer that was asked had some, read when the button was pressed). Ask again replaces the panel; Close removes it. Every text from the provider, the name of the reviewer and the node ids are untrusted and shown as plain text (hidden characters made visible, long texts clamped with "Show more", ids cut). Each error code has its own fixed text (`NOT_FOUND`, `PLAN_NOT_REVIEWABLE`, `AGENT_NOT_FOUND`, `AGENT_NOT_REVIEWER`, `LLM_UNAVAILABLE`, `REVIEW_BUSY`, `REVIEW_PROVIDER`, `REVIEW_INVALID`, `INVALID_PARAMS`, a text for a lost connection or a timeout (an error without a code), and one general text), never the message of the error, and the first two agent codes load the agent list again. `REVIEW_BUSY` says the other review may be one that was cancelled, because Cancel gives the button back while the engine still holds its one place. The state of each plan's review lives in the conversation, so it survives switching chat tabs and closing and opening the chat panel. A review never changes the Deploy button, the flags or the plan, and the card does not read it for anything else. The fake engine (`src/engine/fake-review.ts`, `data.review` scripts the answer, an error or a hang) checks plan, kind and model in the engine's order (a plan that failed or was cancelled is `PLAN_NOT_REVIEWABLE`, an id that was never planned `NOT_FOUND`), allows one review at a time (`REVIEW_BUSY`) and drops a node id the workflow does not have.
- The notes switch is on only when the engine reported at least one note. While `listMemory` is pending or failed, the composer says "Notes not loaded", leaves notes out of the transfer notice and sends `useMemory: false`, so what the screen says is what leaves the computer.

Text written by the model (summary, questions, options, reason, nearest idea, flag messages) and names of attached files are untrusted. They are shown as plain text only, with bidi, zero-width and control characters made visible as `‹U+202E›`, a length cap and a "show more" button. A test reads the sources of `src/chat` and fails on `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `localStorage`, `sessionStorage`, anchors, `href`, `src` and network calls.

### Chat tabs

The panel holds up to 8 chats as tabs. `ChatPanel` owns the header (title, the Chat, Model and Notes switch, the model text and the agent picker), the tab strip and the shared views. Each tab is a `Conversation` (`src/chat/Conversation.tsx`) with its own reducer, draft, attachments, effort, notes switch, deploy state and running request. The list of tabs is a pure reducer in `src/chat/model/tabs.ts`.

- Every tab stays mounted while the app runs, and the inactive ones are hidden. Switching between tabs loses nothing. The tabs also survive closing and opening the chat aside, because the app keeps the panel mounted.
- The tabs live in memory only. After a restart of the app there is one empty chat. Nothing is saved to disk.
- The model list and the notes count are loaded once for all tabs. The Model and Notes views are shared, and the tab strip shows only in the Chat view.
- A tab is titled with its first message, cut to 28 characters and shown as plain text with invisible characters made visible. A tab without a message is called "New chat". There is no New chat button: the plus button after the tabs opens a new empty tab and makes it the active one.
- A tab that has a request running shows an activity indicator. An answer that arrives in a tab the person is not looking at lands in that tab and marks it with a dot until the tab is opened. A request that fails in such a tab marks it the same way, and the failure shows when the tab is opened. A tab that was away scrolls to its newest message when something arrived meanwhile, and otherwise returns to where it was read.
- A tab closes with its x button, or with the Delete key while it has the focus. A tab that has messages, a draft, attached files or a running request asks first. Closing sends `cancelPlan` for the running request and asks the port to remove the files that were not sent. Workflows that were deployed from the tab stay. When such a workflow is deleted, the plan card in the tab (open or in the background) goes back to offering Deploy, as the engine allows a plan to be deployed again.
- Requests at the same time: the engine plans at most 2 at once and answers the next with `PLAN_BUSY`. A second tab can send while the first one waits for its answer. A third request at the same time fails in the tab that sent it, with the text of `PLAN_BUSY`, and the text comes back to the draft of that tab.
- Keyboard: the strip is a `tablist`, each tab has `aria-selected` and `aria-controls`, and each conversation is a `tabpanel` labelled by its tab. The arrow keys, Home and End move the focus between the tabs, Enter or Space opens the focused tab. Only the focused tab and its close button are in the Tab order. The strip scrolls sideways and keeps the active tab in view. The close buttons and the activity marks sit beside the tablist, so the tablist holds only tabs.

### The attachment port (for the real client)

```ts
interface AttachmentPort {
  add(file: File): Promise<AttachmentRef>
  remove?(id: string): Promise<void>
}
```

The panel validates a file before it calls `add`: the media type must be one of the eight in `AttachmentRefSchema`. A declared type of the eight must agree with the extension (`tool.exe` declared as `image/png` is refused; a declared text type may stand for any text extension, including unknown ones like `.log`); a declared type outside the eight, such as `application/vnd.ms-excel` that Windows gives to `.csv`, falls back to the extension. A dropped folder is skipped even when it is named like a file. PDF up to 20 MiB, image up to 3.75 MiB, text up to 1 MiB, not empty, at most 5 files per message and 10 per conversation. `add` must copy the file into the engine's attachment folder and resolve with the protocol `AttachmentRef` (`id`, `mediaType`, `name`, `bytes`). File bytes never go through the protocol. If `add` rejects, the panel shows the localized text of the error code (`ATTACHMENT_REJECTED` and the others) and never the text of the error. `remove` is optional and best effort. The panel calls it for a file that finished adding after the composer was gone, for the unsent files of a chat tab that is closed, and for the unsent files (and those of a request that was cancelled) when the panel is closed.

### Choosing the model

`plan` has no model field: the engine is started with a provider and a model. So `ModelPicker` is controlled. It shows the table of `llmModels` grouped by provider, marks the active model (`aria-current`), disables providers without a key with a "key needed" label, and shows the provider's `dataNote`. Choosing a configured model calls `onSelectModel({ provider, model })` and nothing else: the picker never changes its own selection and never says a switch happened. What the callback does (probably restarting the engine) is for the code that owns the engine.

### Notes

`MemoryPanel` lists, adds, edits and deletes the notes that `listMemory`, `saveMemory` and `deleteMemory` handle (at most 20, one line of at most 300 characters). It shows the rule before the engine says it, a 0/20 and 20/20 state, and the "sent to the model provider with every plan" notice. The add field is off until the list has loaded, and both fields stop at 2000 characters, the limit of the protocol. Errors show the localized message of the code (and of the rule for an invalid note), never the text of a note.

### Looking at it and scripting it

`Chat/ChatPanel` has the whole flow: `Flow` answers the first request with three questions, the second with a workflow that has three flags and the later ones with a plain workflow or an unsupported card, so you can click through questions, flag confirmation and deploy. `Errors` fails each send with a different error code. `Nothing configured`, `Long conversation` and `Patch` are the other states. Every story has a "start over" button that builds a new fake engine.

The fake lives in `src/engine/fake-plan.ts`: `withPlanMethods(client, data)` wraps the Plan 4a fake client and answers `plan`, `cancelPlan`, `deployPlan`, `llmModels`, `listMemory`, `saveMemory`, `deleteMemory`, the agent methods and the rule methods with the rules of the engine (parameters are checked with the real protocol schema, the same plan id twice is `PLAN_EXISTS`, two plans at a time, deploy needs exactly the flag keys, a plan whose workflow was deleted can be deployed again, notes follow the engine's memory rules). `data.script(params)` decides each answer: return `{ result, meta }`, a `RillError`, or `'hang'` (the plan runs until it is cancelled). The data for stories and tests is built in `src/fixtures/plan.ts`, typed with the protocol types.

## Add a story

Every component file in `src/graph`, `src/inspector`, `src/runs`, `src/workspace`, `src/ui`, `src/explain`, `src/recipes` and `src/chat` needs a stories file next to it, and `test/stories-smoke.test.tsx` fails when one is missing.

1. Create `Name.stories.tsx` beside `Name.tsx` with a `Meta` that has a `title` such as `Graph/NodeCard`, and one exported story per state worth seeing.
2. Build the data from `src/fixtures` or with the builders in `src/fixtures/workflows.ts`. Fixtures are typed against `@rill/protocol`, so they cannot drift from what the engine sends.
3. A story that needs state or hooks renders a small named component, because hooks cannot run in a `render` function.
4. Run `pnpm --filter @rill/desktop exec vitest run test/stories-smoke.test.tsx`. It renders every story once in Korean with the light theme and once in English with the dark theme, and fails on a thrown error, a `console.error` or `console.warn`, an empty story, or a message key that shows up untranslated.

Every text a person reads goes through `useT()`. Add the key to both `src/i18n/ko.ts` and `src/i18n/en.ts`; a test fails when the two differ.

## Agents

An agent is a name with a persona and instructions. The planner and the failure explanation follow the active one. The engine owns them (see `packages/engine/README.md`); the renderer reads and changes them only through `listAgents`, `saveAgent`, `deleteAgent` and `setActiveAgent`.

**One state for the whole window.** `src/engine/agents.ts` keeps one store per engine client (`agentsStoreFor(client)`, the hook `useAgents(client)`). It loads the list once when the first component subscribes, keeps the list in the engine's order (the built-in Default first, then the saved agents by name), and runs the writes one after another, so the last choice wins. The chat picker, every chat tab, the Agents screen and the explain panel read the same state, so a change on the Agents tab shows in the chat header at once. `useAgentsState(client)` only watches and never loads: the explain panel uses it, so it sends no request of its own. A write that fails with `AGENT_NOT_FOUND` loads the list again. A write that is answered while a retry of a failed load is still running makes the state `ready` again from the list the window already has (the late list answer is dropped), so the picker is never left on "Loading agents…"; a write answered before the list was ever loaded keeps the state `loading` and loads the list.

**The chat header.** `AgentPicker` is a small select next to the model text: the built-in Default (translated, never the engine's text) first, then the saved assistants. A reviewer agent never appears in it (`assistantsOf` in `src/engine/agents.ts`), because only an assistant can be the active agent. It stays enabled while a request runs, and a running request keeps the agent it started with. Changing it calls `setActiveAgent` and takes effect for the next request of every chat tab. While the list is loading, or has failed, the picker says so, and the requests carry no `agentId` (an absent id means Default), so what the screen says is what leaves the computer. Each `plan` and `explainRun` request carries `agentId` only for a loaded, non-default agent. The transfer notice names "agent settings" when the active agent has a persona, instructions or at least one skill, because the text of its skills goes to the provider too. `MetaLine` adds "Used N skills" when `meta.skillsUsed` is above zero. An answer says which agent made it (`meta.agentUsed`) and when the settings were left out (`meta.agentDropped`). An error from `setActiveAgent` shows the fixed text of its code, and `AGENT_NOT_FOUND` also reloads the list.

**The Agents tab** (between Recipes and Settings). `AgentsScreen` takes the client and, in the app, the host's file dialogs:

- A list on the left (Default first, then the saved agents by name; the selected one has `aria-current`, the one in use has a mark), "New agent", "Import…" and a count out of 12. Each row has a kind chip (Assistant or Reviewer) and, when the agent has skills, their number. A reviewer has no "In use" mark and says that it is asked from a plan card. At 12 agents both buttons are off and a note says why.
- An editor on the right with the four fields, a counter in code points, the rule as a hint, and a message under a field that breaks a rule. The rules are the engine's: `normaliseAgentField` from `@rill/protocol` checks each field as you type, so the screen and the engine cannot differ. Save is off until something changed and every field is valid; Enter in the name field saves; a double submit sends one request. "Use this agent" makes it the active one and is off while the agent has unsaved changes. Delete asks first, names the agent as plain text and says when Default takes over. Default is read only: no field, no Save, no Delete.
- **Kind and skills.** Under the description there is a Kind select (Assistant or Reviewer) with the hint of the chosen kind. It is locked, with the reason, for the agent in use: only an assistant can be in use, so the engine refuses to turn it into a reviewer (`AGENT_NOT_ASSISTANT`). A saved reviewer has no "Use this agent" button; a note says it is asked from a plan card. Below the instructions a Skills group lists every skill as a checkbox with its size and description, a meter "x of 6000 characters" for the checked ones, "n of 8 skills" and the note that skills are used in alphabetical order of their names. A skill that no longer fits (the 8th limit or the 6,000 characters) is off with "Does not fit" and a line says why; Save is also off for a list that is over a limit, so the engine's `skills.*` problems only come back after a race (they have their own fixed texts, for a skill that was deleted meanwhile, too many and too large). A skill that was deleted after the draft was made is dropped from the draft (`withKnownSkills` in `src/app/agents/model/draft.ts`, applied by `selectionOf` once the skills are loaded), so the boxes, the meter and "n of 8 skills" count only skills that exist, a note says that one was removed, and Save stays on for the other edits. When Save is answered with the "skill was deleted" text, the skills are loaded again. The checked ids are sent in the order of the skill names. `saveAgent` carries `kind` and `skillIds` only when they changed from what is stored, so an edit of the text never touches them. While the skills load or fail to load the group says so (with a retry), and with no skill at all it points to the Skills screen. Default has no kind or skills to change.
- Unsaved edits are not lost silently. Leaving the editor for another agent, "New agent" or "Import…" asks first (Keep editing or Discard changes; for Import the question comes before the file dialog opens, and Discard drops the edits and then opens it), and the draft lives in a small store per client (`src/app/agents/model/view.ts`), so an edit survives a visit to another tab (the draft holds the kind and the skill ids, and the skills of the draft are compared as a set).
- Above the screen: what an agent is, and one muted line with the arrow icon that says the persona, the instructions and the skills of an agent go to the model provider with every request the agent is used for, and with every review when it is a reviewer (the hint of the Reviewer kind says so too), with the advice not to write secrets, passwords or personal data in them.
- The text of a name or description from the engine is shown as plain text with hidden characters made visible (`‹U+202E›`) and truncated by the layout. A status line (`role="status"`) says what was done and an alert says what failed, always with the fixed text of the error code.

**Import and export (Markdown).** The file looks like this:

    ---
    name: Terse reviewer
    description: Short answers
    ---

    # Persona

    Calm and brief.

    # Instructions

    Name every default you pick.

A reviewer has one more key after the description, `kind: reviewer`. The key is optional (`kind: assistant` is the same as no key), and the app writes it only for a reviewer, so the file of an assistant is what it always was. Any other value, in any case, is a problem (`invalid_kind`) with its line number. Skills are not part of an agent file: a `skills:` line is an unknown key, and the review screen says that an imported agent has no skills and shows the kind of the file.

`parseAgentFile` in `src/app/agents/agent-file.ts` is strict and written by hand (no dependency): at most 64 KiB, no replacement character (text that was not valid UTF-8), the first line is `---`, the front matter holds only `name:`, `description:` and `kind:` once each on a line of their own, and the two headings are exactly `# Persona` and `# Instructions`, once each and in that order, with nothing but blank lines before the first. Any other line that starts with `# ` is a problem; `##` and deeper headings, a bare `---` and a line like `#tag` are text. One leading byte order mark and Windows line endings are accepted. The text of the persona and the instructions must not contain `agent-profile-` in any case. The fields then pass the same normalisation as a save. Every problem is reported with a plain message and, where it belongs to a line, the line number, never the text of the file. `serialiseAgentFile` writes the same format and refuses an agent that has a line starting with `# ` in its persona or instructions, since that line would not read back.

Import opens the system file dialog (`.md`, one file) and shows a review screen: the file name, the parsed fields, every problem, the line "nothing is saved or switched on yet", and the transfer note. The name and the description can be edited there (a name that already exists, ignoring case, or that is one of the names of the built-in Default agent, must be changed first); the persona and the instructions are shown as they are in the file and are changed by editing the file. Save adds a new agent; the import never makes it active, and cancel saves nothing. Export asks for a file name with the system save dialog and writes the saved agent (it is off while there are unsaved changes).

**The host side.** `dialogs.openText()` returns `{ name, text }` or `undefined` when the dialog is cancelled; `dialogs.saveText({ suggestedName, text })` returns `{ saved }`. Both have TypeBox schemas in `src/shared/host-api.ts` (text up to 64 KiB of UTF-8, a suggested name without control characters or slashes), a preload bridge, IPC handlers and entries in the fake host. `src/main/text-files.ts` reads and writes the file: only a regular file, opened without following links, at most 64 KiB (a larger file is refused from its size before it is read, and one that grew is stopped at 64 KiB plus one byte), and it hands the text over as it is, decoded as UTF-8 with replacement characters, with no parser, no JSON and no normalisation. Errors are the fixed host codes `FILE_TOO_LARGE`, `FILE_REJECTED` and `INTERNAL`; the path and the text never reach a log or an error.

**Fakes and stories.** `src/engine/fake-agents.ts` implements the four methods with the engine's rules and errors (kind, skill ids with `skills.unknown`, `skills.duplicate`, `skills.too_many` and `skills.too_large`, `AGENT_NOT_ASSISTANT` for a reviewer that is made active, named in `plan` or `explainRun`, or that would replace the active agent), and `withPlanMethods` uses it: the fake planner records the `agentId` of every plan request (`planAgentIds()`) and refuses an unknown id before it runs the script. The Storybook groups are `Chat/AgentPicker`, `App/Agents/AgentsScreen`, `App/Agents/AgentList`, `App/Agents/AgentEditor` and `App/Agents/AgentImportReview`; the screen stories click through the editor with errors, the new agent form, the limit, the delete and unsaved prompts, the import review (clean, with problems, not an agent file, hostile text) and the export.

### The Skills screen

A skill is a named block of text (name up to 60 characters, a one-line description up to 200, a text of 1 to 4000 characters with line breaks) that is attached to agents. The engine owns skills (see `packages/engine/README.md`); the renderer uses `listSkills`, `saveSkill` and `deleteSkill`. `SkillsScreen` in `src/app/agents/SkillsScreen.tsx` is the second entry of the Agents tab ("Agents | Skills | Rules"). The draft, the selected skill and the import review live in a small store per client (`src/app/agents/model/skill-view.ts`), so an unsaved edit survives a visit to another screen. The edits belong to the skill they were made on: an edit pins the selection to that skill, and when the skill is gone (another client deleted it, and the list was loaded again after `SKILL_NOT_FOUND`) the screen shows the next skill with its stored text, or the empty form when there is none, never the unsaved text of the deleted one.

- A list on the left with "New skill", "Import…" and a count out of 24 (at 24 both are off and a note says why). Each row has the size in characters, the description and "Used by: " with at most three agent names and a count of the rest, or "No agent uses it". With no skill the form for a new one is open.
- An editor on the right: name, description and text, each with a hint that holds the rule, a counter in code points (red past the limit) and a message under the field. The rules are the engine's (`normaliseTextField` through `normaliseSkillFields`). A line says that the skills of one agent are at most 6,000 characters together, and the engine's refusal of an edit that would break that for some agent has its own fixed text (it names no agent and quotes no text). The agents that have the skill are listed under the form. Save, Undo changes, Export… and Delete behave as on the Agents screen (Save is off until something changed and is valid, a double submit sends one request, leaving with unsaved changes asks first).
- Delete asks first, names the skill as plain text and lists the agents that will lose it ("No agent has this skill" when none does; when the agents could not be loaded the dialog says so instead).
- Above the screen: what a skill is (and that nothing in it is run), and one muted line with the arrow icon that says the text of a skill is sent to the provider with every request of an agent that uses it. Agent and skill names are plain text with hidden characters made visible.

**Import and export.** A skill file has the same strictness as an agent file (64 KiB, UTF-8, front matter, one heading) and one section:

    ---
    name: Receipts checklist
    description: What to check before a receipt is filed
    ---

    # Body

    Before you file a receipt: ...

`parseSkillFile` and `serialiseSkillFile` in `src/app/agents/skill-file.ts` allow only `name:` and `description:` once each, the heading `# Body` once with nothing but blank lines before it, and no other line that starts with `# ` (an export refuses a text that has one). The text `agent-profile-` is refused, because the engine would leave an agent that holds it out of a request. The review screen is the one of agents: nothing is saved before Save, the name and description can be edited, the text is read only, a name that exists (ignoring case) must be changed, an import never attaches the skill to an agent, and the sent-to-the-provider line is shown. **Fakes and stories.** `src/engine/fake-skills.ts` implements the three methods with the engine's rules and errors (`SKILL_INVALID` with the problem lines, `SKILL_DUPLICATE`, `SKILL_FULL` at 24, `SKILL_NOT_FOUND`, and the refusal of an edit that would break an agent), and `withPlanMethods` uses it together with the agents (`data.skills` seeds it; a deleted skill is taken off every agent). The Storybook groups are `App/Agents/SkillsScreen`, `SkillList`, `SkillEditor`, `SkillImportReview` and `SkillsPicker`, and the Agents stories gained the kind chips, the picker, a reviewer and the import of a reviewer file.

- A line at the top says that rules limit agents, plans, recipes and imported workflows, apply to everything that is deployed, activated or run, and change only on this screen. Removing the cap with "No cap" asks with the remove dialog. Cancel puts the select back on the saved cap. It is off when all 30 places are used and there is no cap to replace.

Names and messages come from the engine and are shown as plain text, with hidden characters made visible and the length cut (80 characters for a name, 200 for a message). An older answer that ends after a newer request is dropped. ### The Hooks screen

The third entry of the sub-navigation, "Hooks" (`id: 'hooks'`), opens `HooksScreen` in `src/app/agents/HooksScreen.tsx`. It takes the client, the connections of the settings (`settings.connections`, or `undefined` while the settings are not loaded) and an optional `onOpenConnections`, which the app wires to "Settings, Connections". The engine owns the hooks (see `packages/engine/README.md`, "Hook methods"); the screen reads and changes them only through `listHooks`, `saveHook`, `deleteHook` and `listHookLog`.

**State.** `src/engine/hook-store.ts` keeps one store per engine client (`hookStoreFor(client)`, the hook `useHookStore(client)`), like the rules store. It loads the list when the first component subscribes, asks again when the last load failed, runs the writes one after another and loads the list again on a `workflow.deleted` event (the engine deletes the hooks of a deleted workflow with it). A write that finishes while such a load is on its way starts a new load, so the old list is never written back over the answer. A write that failed loads the list again, because a lost answer may hide a hook that the engine saved, or a hook that is gone (`HOOK_NOT_FOUND`, `HOOK_FULL`, a duplicate that the list does not show); only `INVALID_PARAMS` and a `HOOK_INVALID` that is not a duplicate leave the list as it is. The activity log is kept apart: `refreshLog()` asks `listHookLog` for the last 50 rows (`HOOK_LOG_DEFAULT_LIMIT`), keeps the rows that it has while it loads or fails, and lets the newest answer win. The screen calls `refreshLog()` when it opens and on the Refresh button, and at no other time.

**The checks are the engine's.** `src/app/agents/model/hooks.ts` builds the input of `saveHook` from the form and judges it with `checkHookInput` and `hookKey` of `@rill/protocol`, so the form refuses what the engine refuses and nothing else: the connection must be saved and of kind `slack` and a notice must not be forbidden by a rule (both only while the hook is switched on, so a hook can always be switched off), the channel and the count follow the engine's grammar and range, a hook with the same event, workflow and action is a duplicate (the hook being edited is not), and a switch off is only for a failed run. The event and the action are never in a refused combination: while the event is not "A run fails" the switch off is a disabled option, and while the switch off is chosen the other two events are disabled, so nothing changes by itself. `hookErrorKey` gives a fixed text for `HOOK_INVALID` (the first problem line that `parseHookProblemLine` can read, one text per rule), `HOOK_FULL`, `HOOK_NOT_FOUND`, `INVALID_PARAMS` and any other error. The text of the engine's error is never shown.

- **The page.** The title is hidden with the visually hidden style, because the sub-navigation names the screen. Three muted lines say what a hook is (and that it never starts a run, a plan or a model call), that hooks run in the engine so they work with the window closed (and replay nothing after a stop), and, with the small arrow icon of the quiet transfer notice, that a Slack notice goes to Slack with the workflow name in a fixed sentence. A count says "N of 20 hooks"; at 20 New hook is off and a note says why, and editing stays possible.
- **The list.** One row per hook: the event, the workflow (a name from the engine, shown as text with hidden characters made visible and the length cut to 80 characters, or "All workflows"), the action in words, a switch with On or Off, Edit and Delete. Every control has a label that names the hook. A notice that a rule blocks, or whose connection is not saved any more, says so in the row, and its switch cannot be turned on. The switch sends the whole hook with the other flag. Delete asks first and names the hook, the dialog tells that its rows in the activity stay, and the focus goes to the heading of the list afterwards.
- **The form.** Opens above the list with its heading focused. Fields: when (the event), for (All workflows or one workflow), then (the action), and for a notice the Slack connection (only the saved Slack connections; one that is not saved any more stays as "name (not saved)"; with none, the hint "Add one in Settings, Connections" with the button when the screen can open it, and plain text when it cannot), the channel, and a message preview; for a switch off a number field from 2 to 20; and a switch for "Switch this hook on". The preview is `hookMessage(event, name)` of the protocol, the fixed English sentence with the name that the engine would send (a name with `<`, `&` or quotes already made safe), and `Workflow "<name>" failed.` while the scope is all workflows. The form hints at a hook that can never post: a webhook connection with a channel, and a bot connection with neither a channel nor a default channel (it can still be saved, as the engine allows). Save is off until the form is complete, changed and without a problem; two quick presses send one request. Cancel puts the focus back on the button that opened the form, and Save on the Edit button of the hook. Opening another hook while the form has changes asks first. The form with what was typed in it lives in a small view store of the client (`src/app/agents/model/hooks-view.ts`, like the draft of an agent), so it is still there when the person looks at Rules, visits another tab, or follows "Open Settings, Connections" to add a connection and comes back; Cancel, a saved hook and a hook that is gone drop it.
- **Activity.** The last 50 rows of the log, newest first: the result as a word in a coloured chip (Done, Failed, Skipped in cooldown, Skipped limit reached, Blocked by a rule, Nothing to do; never colour alone), the fixed code of a failure with its meaning in words (as the title of the code and as text that only a screen reader reads, so that `http_status` is not spelled out), the time (`formatTimestamp`, with the optional `timeZone` prop for stories and tests), the action of the hook in words, the event, and the workflow as text. The log keeps no copy of the action, so the words are the action that the hook has now and the row says so ("Now: ..."); a failure of a Slack notice that was later changed to "Write to the activity log only" is not shown as a failure of the log action. A row of a hook that is not in the list reads "Deleted hook", and a workflow that is not in the list reads "A workflow whose name is not available". A count in a status element says how many rows are shown; a failed load is an alert, and the rows that were shown stay. A closed "What the results mean" part explains each result and each code. The panel appears when the hooks are loaded, so no row is called a deleted hook before the list is known.
- **Live regions.** One status element stays in the page and holds what happened (created, saved, deleted, switched on or off). An error of the form is an alert inside the form, an error of a switch or of a load an alert on the page, and an error of a delete an alert in its dialog. A switch that the engine refuses for a connection, a workflow or a rule (things only the form can change) says on the page that the hook cannot be switched on as it is saved and to choose Edit, since there is no list to choose from there. While a switch or Save waits for the engine its controls are off, and the browser then drops the focus of the one that had it; the screen gives the focus back to that control when the answer comes (the switch, or the field or button of the form, also after a failed save), unless the person moved the focus meanwhile. A refused save of a hook that is gone closes the form and puts the alert on the page.

**Fakes.** `src/engine/fake-hooks.ts` implements the four methods with the engine's rules and errors (it calls `checkHookInput`), and `withPlanMethods` uses it: `data.hooks` and `data.hookLog` seed it, `data.connections` (a list, or a function that may answer later) gives the saved connections, and `client.hooks.addLog(entry)` adds a row. The fake world passes the hooks and the log it is given, answers `listWorkflows` for the hooks from its own list of workflows, and reads the connections from the fake host, so a hook can be saved for a workflow of the world and a Slack connection of the settings; deleting a workflow deletes its hooks. The Storybook stories use `HooksStage` (`src/app/agents/HooksStage.tsx`) and the fixtures in `src/fixtures/hooks.ts`.

## The explain panel

`ExplainPanel` in `src/explain/` takes an `EngineClient`, the open run and two callbacks. It never starts a run, turns a workflow off or sends a chat message by itself.

## The recipe panel

`RecipePanel` in `src/recipes/` shows the gallery, then the form of the chosen recipe, then the draft preview.

    interface RecipePanelProps {
      client: EngineClient
      catalog: readonly NodeInfo[]
      connections: readonly { name: string; kind: 'slack' | 'http' | 'webhookSecret' | 'google' | 'microsoft'; account?: string; reconnect?: true }[]
      onPickPath?(kind: 'folder' | 'file'): Promise<string | undefined>

The host contract:

- The protocol has no method that lists connections (the engine reads them from a file at start), so the host passes `connections`. A connection field is a select of the entries whose `kind` matches the param's `connectionKind`. With none it shows a message and no free text.
- The Google and Microsoft accounts are not saved connections. `App` turns the accounts of the settings (`settings.oauth.accounts`) into entries named `google` or `microsoft` with the kind of the same name and gives them to the panel next to the saved connections (`connectionsWithAccounts` in `src/recipes/model/values.ts`). A connected account carries its account text; an account that needs to be connected again carries `reconnect: true`; an account that is not set up, not connected or being connected is left out. A parameter with `connectionKind` `google` or `microsoft` lists only the account of that provider, and a Slack or http parameter never lists an account. The account that needs to be connected again is shown disabled, with the reason in its label and in a note under the field, and counts as no choice, so the form cannot be submitted with it. With no account the field shows "No Google account is connected. Connect it in Settings, Connections first." and no select. The window sends the name only; the account text is shown as text and never leaves the form.
- `onPickPath` is for a native folder or file dialog (Plan 4d). Without it a folder or file field is a plain text input. A cancelled or failed pick leaves the text alone.
- The form checks only what costs nothing: required, 500 characters, a number range, and text with `{{` or `}}`. Every other rule comes back from `instantiateRecipe` as `RECIPE_INVALID` problems and is shown at the field or in a list. The rule and issue tables are in `src/recipes/model/problems.ts`.
- The cron field has labelled presets and no parser; the server checks the expression.

## Rules for renderer code

`src/` runs in a browser, so it must stay browser-safe:

- It may import types and pure code from `@rill/dsl` and `@rill/protocol`, and only types from `@rill/nodes-core`.
- It must not import `@rill/engine`, `@rill/planner`, `@rill/llm`, `@rill/recipes`, `@rill/eval` or any `node:` module. An ESLint rule, a test that reads the sources and a test that builds every source file for the browser all enforce this.
- Run data (step input and output, errors, trigger payloads) is untrusted. Show it only as text. `dangerouslySetInnerHTML`, `innerHTML`, `eval` and links made from run data are banned, and the tests render `<img onerror>` and `<script>` strings to check that they stay text.
- `src/explain/` and `src/recipes/` also may not use `localStorage`, `sessionStorage` or a runtime import of `@rill/recipes` or `@rill/planner`; `test/panels-source.test.ts` reads the sources and fails on each. Model text, recipe text and ids from the server are shown only as text, with no link made from them.
- Status is never shown by color alone: every status has its own icon and a word. A test computes the contrast of every text and background token pair in both themes and requires 4.5 to 1.
- Times are formatted with `Intl` from a `now` prop and an optional `timeZone`, so stories and tests give the same output every day.

### Run it

From the repository root, in your own terminal (this starts a server and a window, so the build agents never run it):

    pnpm install

### Build the installer

    pnpm --filter @rill/desktop dist

This builds the engine bundle and the app, then runs electron-builder. The result is in `apps/desktop/release/` (git ignores it): a `dmg` and a `zip` for the architecture of the machine that built them, for example `Rill-0.0.0-arm64.dmg`. The app id `app.rill.desktop` is a reverse-DNS placeholder until there is a real domain, and the default Electron icon is used.

If the repository sits in a folder that iCloud Drive syncs (on a default Mac setup `~/Documents` does), the build fails at the signing step with "resource fork, Finder information, or similar detritus not allowed", because the sync adds extended attributes to the packed app. Build into a folder that is not synced instead:

    pnpm --filter @rill/desktop dist -c.directories.output=/private/tmp/rill-release

The build is signed ad hoc (identity `-`), not with a developer certificate, and is not notarized, because there is no signing identity yet. The ad hoc signature verifies (`codesign --verify --deep --strict`), but Gatekeeper does not trust it. On another Mac a downloaded copy is blocked. Remove the quarantine flag once with `xattr -dr com.apple.quarantine /Applications/Rill.app`, or try to open the app once and then use System Settings, Privacy & Security, Open Anyway. Right click, then Open, no longer works on current macOS.

electron-builder also flips the Electron fuses of the packed binary (`electronFuses` in `electron-builder.yml`): `runAsNode`, `enableNodeOptionsEnvironmentVariable`, `enableNodeCliInspectArguments` and `grantFileProtocolExtraPrivileges` are off, `enableEmbeddedAsarIntegrityValidation` and `onlyLoadAppFromAsar` are on. So `ELECTRON_RUN_AS_NODE`, `--inspect` and `NODE_OPTIONS` do nothing in the packed app. `test/main-packed-app.test.ts` reads the fuses and the signature of the packed app when `release/` holds one, and skips otherwise.

### Where data lives

Everything is in `~/Library/Application Support/Rill`:

| File | Content |
| --- | --- |
| `config.json` | Allowed folders, provider, model, the login setting and the language (`system`, `en` or `ko`; a file from an older version without it, or with a value that is not one of these, reads as `system` and keeps the other settings). No secrets. A corrupt file is kept as `config.json.bak` and the defaults are used. |
| `secrets.bin` | The provider keys, the connection secrets (with the auth type of a custom connection, which is not secret) and the Google and Microsoft sign-in records (the Client ID and Client secret of each app, and the refresh token, scope, account text and sign-in time of each account), encrypted as one blob with Electron `safeStorage`. The blob keeps `"version": 1` while nothing is stored for the sign-in, so an older app reads it, and becomes `"version": 2` with an `oauth` section when something is; an older app then treats the file as unreadable and moves it aside to a `.bak` file instead of dropping the section. Access tokens are never written to it. A file that cannot be decrypted is moved to `secrets.bin.bak` (or `secrets.bin.bak.1` to `.9` when that name is taken; no backup is ever overwritten) the next time a key or connection is saved, and the keys must be entered again. When all ten names are taken, saving is refused. |
| `rill.db` | The engine database (workflows, runs, plans, memory, agents and the active agent). |
| `attachments/` | Files the user attached, copied there as `<id>.<ext>` with mode 0600 in a folder with mode 0700. At most 500 files and 512 MiB in total; a file over either limit is refused with `ATTACHMENT_REJECTED`. Half-written `.partial-*` files left by a crash are removed at start. |

When `safeStorage` is not available (no keychain), saving a key or a connection is refused with a clear error and the engine is not started. There is no plaintext fallback. The window never receives a secret: settings return only which providers have a key, the name, kind and auth type of each connection, and for each account its status and account text, the Client ID of its app and whether a Client secret is saved. The engine gets a secret only through the environment of its process: the key of the chosen provider in its own variable (`ANTHROPIC_API_KEY` and so on) and the connections as JSON in `RILL_CONNECTIONS`. No connections file is ever written. The environment of a process is not private on macOS: any process of the same user can read the original environment block of the engine (for example with `ps -E -p <pid>`) without a keychain prompt, and the engine cannot hide it by deleting the variables. This is a known limit of passing secrets by environment. The token alone is enough to drive the engine over `ws://127.0.0.1`. Moving the secrets to a message channel needs a change in the engine CLI and is not done here.

To reset the app, quit it, delete `~/Library/Application Support/Rill`, and delete the keychain item that `safeStorage` made for the app (open Keychain Access and search for "Safe Storage"; the item is named after the app, and "Electron Safe Storage" when started from `dev`).

### The key check

When you save a provider key in Settings, the main process first asks the provider whether it accepts the key (`src/main/key-check.ts`). The request is made by the main process because the window's content security policy allows no outside connection. It is one `GET` of the provider's model list, which is read only and costs nothing:

| Provider | Address | Header that carries the key |
| --- | --- | --- |
| Anthropic | `https://api.anthropic.com/v1/models` | `x-api-key` (and `anthropic-version: 2023-06-01`) |
| OpenAI | `https://api.openai.com/v1/models` | `Authorization: Bearer` |
| Gemini | `https://generativelanguage.googleapis.com/v1beta/models` | `x-goog-api-key` |
| Grok | `https://api.x.ai/v1/models` | `Authorization: Bearer` |
| Meta | `https://api.meta.ai/v1/models` | `Authorization: Bearer` |

The addresses are a constant keyed by provider, so nothing the user types reaches an address or a header name. The key is never put in a URL or a query string. No cookies are sent, redirects are refused, the request has the generic `User-Agent: Rill`, and it gives up after 10 seconds. The response body is not returned or stored. For a status 400, and for a 401 from OpenAI, it is read, up to 4 KiB, only to look for the provider's known wording.

The answer becomes one of three verdicts. The rule is conservative: only a clear rejection blocks a key.

| Answer | Verdict | Reason |
| --- | --- | --- |
| 2xx | `valid` | |
| 401 | `invalid` | `unauthorized` |
| 401 from OpenAI whose body says "insufficient permissions" or "missing scopes" (a restricted project key without the model-list scope) | `unverified` | `forbidden` |
| 400 whose body has Gemini's `API_KEY_INVALID` or Grok's "incorrect api key" or "invalid api key" wording | `invalid` | `rejected` |
| Any other 400 | `unverified` | `unexpected_status` |
| 403 | `unverified` | `forbidden` (some providers answer 403 for a valid key in a region they do not support) |
| 429 | `unverified` | `rate_limited` |
| 5xx | `unverified` | `server_error` |
| Network error, refused redirect | `unverified` | `network` |
| No answer in 10 seconds | `unverified` | `timeout` |
| Any other status | `unverified` | `unexpected_status` |

A key that has a space, a control character or a non-ASCII character cannot be sent in a header and cannot be an API key, so nothing is sent: the verdict is `invalid` with the reason `malformed`, and the call throws the host error `KEY_MALFORMED` before anything is saved, with or without `saveAnyway`. The notice then says what is wrong with the key, and has no "save anyway" button. Nothing is sent either when there is no keychain.

`window.rill.secrets.setProviderKey(provider, value, options?)` returns `{ verdict }`. A `valid` or `unverified` key is saved, as before, and the verdict is returned. An `invalid` key is not saved and the call throws the host error `KEY_INVALID`, which crosses the process boundary as the code only. With `{ saveAnyway: true }` the key is checked again and saved whatever the verdict, except a malformed one. Calls for the same provider are ordered by the main process: a save or a removal replaces every earlier save of that provider that is still waiting for its check, and the replaced call throws `SUPERSEDED` and saves nothing, so a slow check can never write an older key over a newer one. The engine restarts only when something was saved and the key of the chosen provider changed, as before.

The Keys section shows "checking" while the request runs, then one of: saved and accepted, saved but not confirmed (with the reason in plain words), or refused with a "save anyway" button. The typed key is held in component state only while the refusal notice is open, and is dropped on save, close, edit or when the row goes away (a refusal that arrives after the row has gone is not kept). The result is in a live region and takes the focus.

The addresses, the headers and the 400 wording come from the vendors' documentation. This project has not called them live yet, so the rule above is untested against the real services: treat a wrong verdict as possible. Because only a clear rejection blocks and "save anyway" always exists, a wrong guess costs one extra click, never a key that cannot be saved. `createFakeHost` takes a `keyChecks` option (a function from provider and key to a verdict, `valid` by default) so stories and tests show every state without a network.

### Slack bot connections

Slack does not need sign-in. You create your own Slack app, install it to your workspace and paste its Bot User OAuth Token (`xoxb-...`) into the Slack card of Settings, Connections. Sign-in (OAuth) is not used because Slack treats a `localhost` redirect as a desktop redirect only for apps that opted into PKCE, and a desktop redirect cannot request bot scopes. The normal flow needs an HTTPS redirect, and a local app without a server has none.

The card has a status chip (Not connected until a bot is saved, Connected when Slack confirmed a saved token, Not confirmed when every saved token was saved without Slack's confirmation), a collapsible "How to get a bot token", then the form: a name, the bot token (a password field) and an optional default channel. The four steps are: create an app at `api.slack.com/apps`; under OAuth & Permissions add the bot scope `chat:write` (and `chat:write.public` to post in channels the bot has not joined); Install to Workspace; copy the Bot User OAuth Token, which starts with `xoxb-`. A note next to the field says that saving asks Slack whether the token works and sends no message. The saved list shows the name, a "Bot" chip, "`<bot>` in `<workspace>`" when the check was confirmed, the default channel, a "Not confirmed" chip when Slack did not confirm that token, and a Remove button. Typing the exact name of a saved Slack connection replaces it (a note says so), which is how a token is rotated or an old webhook becomes a bot; a name that differs only in case, or the name of another kind of connection, is still refused. A webhook connection that was saved earlier shows a "Webhook (old)" chip and keeps working until it is removed; the app no longer creates webhook connections.

When you save, the main process asks Slack whether the token works (`src/main/slack-check.ts`). The window cannot do it because its content security policy allows no outside connection. It is one `POST` with no body to `https://slack.com/api/auth.test`, which posts nothing to any channel. The address is a constant, the token is only in the `Authorization: Bearer` header, no cookies are sent, redirects are refused, the request has the generic `User-Agent: Rill`, and it gives up after 10 seconds. The answer body is read up to 16 KiB. The rule is the same conservative one as the key check: only a clear rejection blocks the token.

| Answer | Verdict | Reason |
| --- | --- | --- |
| HTTP 200 and `ok: true` | `valid` | carries the workspace (`team`) and the bot (`user`) when they are strings |
| HTTP 200 and `ok: false` with `invalid_auth`, `not_authed`, `token_revoked`, `token_expired` or `account_inactive` | `invalid` | `unauthorized` |
| HTTP 401 | `invalid` | `unauthorized` |
| HTTP 200 and `ok: false` with `ratelimited` | `unverified` | `rate_limited` |
| HTTP 200 and any other `ok: false` | `unverified` | `forbidden` |
| 403 | `unverified` | `forbidden` |
| 429 | `unverified` | `rate_limited` |
| 5xx | `unverified` | `server_error` |
| Network error, refused redirect | `unverified` | `network` |
| No answer in 10 seconds | `unverified` | `timeout` |
| A body that is not the expected JSON, or any other status | `unverified` | `unexpected_status` |

The workspace and bot names come from Slack and are untrusted text: control characters, bidirectional overrides and any text that holds the token are removed, they are cut to 80 characters, and the window shows them as text only.

`window.rill.secrets.setSlackBot({ name, token, channel? }, options?)` returns `{ verdict }`. The main process checks the arguments (the token must match `^xoxb-[A-Za-z0-9-]{10,200}$`, the channel is 1 to 80 characters without blanks or control characters), refuses a missing keychain with `NO_KEYCHAIN` and a name that another connection of any kind uses, ignoring case, with `NAME_COLLISION` (a saved Slack connection of the exact same name is replaced), and only then asks Slack. A `valid` or `unverified` token is saved. An `invalid` token is not saved and the call throws the host error `TOKEN_INVALID`, which crosses the process boundary as the code only. With `{ saveAnyway: true }` the token is checked again and saved whatever the verdict. Calls for the same name are ordered like the key check: a newer save or a removal replaces every earlier save of that name that is still waiting, and the replaced call throws `SUPERSEDED`. The engine restarts only when something was saved.

The stored entry keeps the kind `slack` and, as its secret, the JSON text `{"rillSlack":1,"token":"xoxb-...","channel":"#alerts"}` (the channel is optional), which the main process builds from the validated object. `notify.slack` tells a webhook URL, this JSON and a plain `xoxb-` token apart (see "Connections file" in the engine README). The summary that reaches the window has an optional `slack: { mode: 'bot', confirmed?, account?, channel? }` and never the token. `confirmed` is true only when the check was `valid`. A connection without it is a webhook. Files saved before this version load unchanged.

The card shows "checking" while Slack is asked (the form is disabled and a second submit sends nothing more), then one of: connected ("Connected as `<bot>` in `<workspace>`"), saved but not confirmed (with the reason in plain words), or refused with a "save anyway" button. The typed token is held in component state only while the refusal notice is open, and is dropped on save, close, edit or when the card goes away. The result is in a live region and takes the focus.

The endpoint, the headers and the error codes come from Slack's documentation. This project has not called `auth.test` live yet, so the rule above is untested against the real service: treat a wrong verdict as possible. Because only a clear rejection blocks and "save anyway" always exists, a wrong guess costs one extra click, never a token that cannot be saved. `createFakeHost` takes a `slackChecks` option (a function from the token to a verdict, `valid` with a sample workspace and bot by default) so stories and tests show every state without a network.

### Google and Microsoft sign-in

The Google and Microsoft cards of Settings, Connections let the spreadsheet nodes use your own accounts. **The flow was read from the providers' documentation and has not been run against the real services**: no real account, Client ID or provider endpoint was used to build or test it. The endpoints, scopes and behaviours below are the first thing to check when something is refused; every one of them is a constant in `src/main/oauth-providers.ts`, one row per provider with a note per constant, so a wrong value is a one-line fix.

**What you do once per provider.** You create your own app in the provider's console (Rill ships no shared app: a shared Google app would need Google's review for sensitive scopes, and a local app has no server where a secret could stay hidden), then paste its Client ID into the "Set up" part of the card and press Save app settings. The card holds the numbered steps:

- Google: open the Google Cloud console, create or pick a project, enable the Google Sheets API, set up the OAuth consent screen (user type External, status Testing, your own account as a test user), create credentials of type OAuth client ID, application type Desktop app, and copy the Client ID and the Client secret (the console may show the secret only when the client is created, so copy it then). Google issues a Client secret for a Desktop client and does not treat it as confidential. The card requires it for Google, because Google's token endpoint is reported to refuse a Desktop client that sends no secret, even with PKCE; that was not checked against the real service. Rill sends it with every token request. **There is no redirect address to register.** A Desktop client accepts any address on the loopback interface, so Rill uses a temporary one while you sign in. An app that stays in Testing loses its refresh token after about 7 days; publishing the app removes that limit.
- Microsoft: open the Microsoft Entra admin center, App registrations, New registration; supported account types "accounts in any organizational directory and personal Microsoft accounts"; under Authentication add the platform "Mobile and desktop applications" with the redirect address `http://localhost/oauth/callback`; under API permissions add the Microsoft Graph delegated permissions `Files.ReadWrite`, `User.Read` and `offline_access`; copy the Application (client) ID. A Microsoft public client has no Client secret, and the card has no field for one. **The card shows `http://localhost/oauth/callback` in a read-only block with a Copy button, because Microsoft requires the redirect address to be registered.** Microsoft ignores the port of a loopback address but still compares the path, so the registered address carries the path `/oauth/callback` that Rill uses, and one registration covers every sign-in. Microsoft ends a sign-in after 90 days without use.

Copy tries the system clipboard first. The window denies every permission, so when the clipboard refuses, the button selects the address and uses the older copy command, and when that fails too it says so and the address stays selectable by hand. That fallback was not tried in the packed app.

**The sign-in.** Connect opens the system browser on the provider's authorize address. The main process, not the window, builds that address from constants, the Client ID and generated values (a PKCE verifier and challenge, S256; a random 32 hex character `state`); the window never supplies an address. It also starts a one-shot HTTP server on `127.0.0.1` with a port that the system picks. The server answers only `GET /oauth/callback` and only when the `Host` header is the loopback address with that port; anything else gets 404. A callback with a wrong or missing `state` is answered 400 and ignored, and the flow goes on waiting. The first callback with the right `state` wins and the server closes. The reply page is one fixed text that reflects nothing it was sent. The flow ends after 3 minutes (`OAUTH_TIMEOUT`), when you press Cancel (`OAUTH_CANCELLED`) or when the provider reports an error (`OAUTH_DENIED`; its text is never shown). Only one sign-in runs at a time (`OAUTH_BUSY`).

Then the main process exchanges the code at the token endpoint (a form `POST`, no cookies, redirects refused, 15 seconds, the answer limited to 64 KiB). It requires a refresh token and that the granted scope contains every scope the nodes need, because Google lets you untick scopes on its consent screen; otherwise it stores nothing and answers `OAUTH_SCOPE_MISSING` (for Google it first asks Google to revoke the grant that it just received, best effort). It asks the provider's user endpoint for the account name; if that fails the account is still connected and shows as Connected without a name. Every other failure is `OAUTH_EXCHANGE_FAILED`. The card shows the account as "Connected as `<name>`". The name comes from the provider, so it is untrusted: control and direction characters are removed, it is cut short, and it is shown as text only.

**What is stored where.**

| What | Where | Notes |
| --- | --- | --- |
| Client ID and Client secret | `secrets.bin`, encrypted with `safeStorage` | The window gets the Client ID back and whether a secret is saved, never the secret. The secret field is a password field, cleared when you press Save. |
| Refresh token, granted scope, account text, sign-in time | `secrets.bin` | Never leaves the main process. |
| Access token | Memory of the main process and of the engine only | Never written to a file. It lives about an hour. |

Saving new app settings for a provider that is connected disconnects it first (a new app needs a new sign-in), and Remove app settings deletes the Client ID, the secret and the account after a confirmation.

**Keeping the sign-in fresh.** The main process refreshes the access token 5 minutes before it expires (with a small random jitter, never sooner than 5 seconds from now), once at app start, while the window is already open and before the engine starts (waiting at most 10 seconds; when the network is down the engine starts without the token and the refresh is retried), and after the computer wakes. One refresh per provider runs at a time. When the answer carries a new refresh token (Microsoft rotates it), it is written to the encrypted file before the new access token is used or sent anywhere. Network errors, 5xx and 429 retry after 30 seconds, 1, 2 and then every 5 minutes, and a `Retry-After` is honoured. When the provider answers `invalid_grant` or `invalid_client` (access withdrawn, a Google app in Testing after 7 days, Microsoft after 90 days without use), or answers 400 with `unauthorized_client` or `invalid_request` (a request that sending it again cannot cure), the refresh token is deleted, the connection is removed from the engine, the card shows Reconnect needed with a Reconnect button, and a workflow that uses it fails with the spreadsheet node's own text. The app also tells you wherever you are: one notice, "Your Google account needs to be connected again." (or Microsoft, or both accounts in one sentence when both need it at start), with an Open Connections button that opens Settings, Connections. It shows when an account moves to that state while the window is open and once at start when the settings already say so; it does not repeat for a second event with the same state, a failed retry of the sign-in, or your own Disconnect. The text is fixed and never includes the account name. A spreadsheet step that is refused with a 401 in the middle of a run asks for a new token and repeats the call once (see below).

**How the engine gets the token.** The engine keeps the access token in a connection named `google` or `microsoft` with the kind of the same name. At start the token goes into `RILL_CONNECTIONS` like any other connection; after that the main process posts `connection.set` and `connection.remove` messages to the engine over the parent channel of the utility process (see the engine README), so a new token needs no restart. Whenever the engine reports running, the main process sends the current tokens again and tells the engine to forget every account that has no live token, so an account that was disconnected while the engine was starting does not keep the token that its environment carried. The planner sees the connection by name and kind and never the token.

**A token that expires during a run.** When Google or Microsoft refuses a spreadsheet call with HTTP 401, the node asks the engine to renew the token, and the engine posts `{ "type": "connection.renew", "name": "google" }` (or `microsoft`, no other key) to the main process. The main process hears it only from the engine of the current start, accepts only that exact shape, checks that the account is connected, and runs the same single refresh that the timer uses, so a refresh that is already running is shared and not repeated. A request that follows another answered request of the same provider within 30 seconds gets no refresh, so a token endpoint that keeps answering 401 cannot be hammered. The answer is the usual `connection.set` with the new access token, after a rotated refresh token was saved. When the provider has withdrawn the access, the account moves to Reconnect needed and the engine gets a `connection.remove`. After a temporary failure nothing is answered and the engine stops waiting after 20 seconds. Either way the step fails with the same text as before, and the node repeats the call at most once. Only the provider name is ever logged for a request. The refresh token and the Client secret never leave the main process.

**Disconnect.** For Google the app asks Google to revoke the refresh token (best effort, errors ignored). Microsoft has no such call here, so Disconnect is local; the card tells you that you can remove the app's access on your Microsoft account page.

**Try it with your own accounts.** This project could not test against the real providers, so please try these in order and tell the maintainer what happens:

1. Create the app in the provider's console with the steps on the card. For Microsoft, register `http://localhost/oauth/callback` exactly as shown.
2. Open Settings, Connections, open "Set up" on the card, paste the Client ID (and the Client secret, which the card requires for Google), press Save app settings. The card should show the Client ID and "Client secret saved".
3. Press Connect. The browser should open on the provider's consent page. Allow every permission. The card should switch to "Connected as ..." within a few seconds. If you press Cancel, deny, or wait 3 minutes, the card should say so and stay not connected.
4. Run a spreadsheet node: ask the chat for "append a row to my Google Sheet" (give it the spreadsheet id from the address of the sheet) or to an Excel table in OneDrive (the workbook needs a table), and run the workflow. Check that the row arrived.
5. Wait for the token to refresh (about an hour) and run again, or put the computer to sleep and wake it, then run again.
6. Press Disconnect and check that the workflow now fails with an unknown connection.
7. If something is refused, send back: which provider, which step failed, the error sentence on the card, and, for a refused sign-in, the error text that the provider's page showed in the browser. Do not send the Client secret, a token, the address of the browser at the end of the sign-in (it holds a one-time code) or the contents of `secrets.bin`. The app deliberately keeps the provider's error text out of its own logs and messages, so the browser page is the only source of it.

### Connections and API keys

The Connections section of the settings has four parts: Accounts, Slack, Custom connection and Other saved secrets.

- Accounts: a card for Google and one for Microsoft, described under "Google and Microsoft sign-in" above. Slack is not a sign-in account: see "Slack bot connections" above.
- Custom connection: a name and an Auth type, as in the Authorization tab of an API client. No Auth sends nothing. API Key adds a key name and a value to a header or to the query string. Bearer Token sends `Authorization: Bearer <token>`. Basic Auth sends `Authorization: Basic` with the base64 of `username:password`. The fields change with the type, and changing the type clears every secret field. A custom connection is chosen in the `auth` setting of an HTTP request node. A name must differ from every other connection of any kind, ignoring case.
- Slack: the bot token card described below. It sits between Accounts and Custom connection.
- Other saved secrets: webhook signing secrets that were saved before. The part shows only while one exists, with a Remove button. New ones cannot be created here.

A saved connection is of kind `slack`, `http` or `webhookSecret`. The kinds `google` and `microsoft` are not saved connections: the engine holds a connection named `google` or `microsoft` only for a signed-in account, and only the sign-in creates it. So `secrets.setConnection` refuses those kinds, and a saved connection cannot be named `google` or `microsoft` in any case (`NAME_COLLISION`; an older secrets file that holds a saved connection of those kinds loads, and the entry is dropped).

A custom connection is stored as a connection of kind `http`. Its secret is a JSON text with `"rillAuth": 1` and the auth fields, which the main process builds from a validated `CustomAuth` object (`host.secrets.setCustomConnection`), so the window never assembles a secret string. `http.request` recognises that format (see "Connections file" in the engine README), and any other `http` secret keeps its older meaning. The list shows the name and an auth type chip only.

The host API has `secrets.setCustomConnection`, `secrets.setSlackBot`, `oauth.setApp`, `oauth.clearApp`, `oauth.connect`, `oauth.cancel`, `oauth.disconnect`, `oauth.onChanged`, `authType` and `slack` on each connection summary, `Settings.oauth` (`available`, `accounts` and `apps`) and the error codes `TOKEN_INVALID` and the `OAUTH_*` codes. `OAuthProvider` is `'google' | 'microsoft'`. In the API keys section, a provider that has a key shows sixteen bullets as the placeholder of its field, next to the Configured chip. The placeholder is the same fixed text for every key and is never derived from a key. Typing replaces it, and no host call returns a key.

### Logo and icons

The mark is a water drop (a rill is a small stream) with a stream that splits in two inside it. The sources are SVG files in `build/`: `icon.svg` is the macOS app icon (a rounded tile with the drop, drawn inside the 824 px safe area of a 1024 px canvas), `icon-small.svg` is the same tile with one dot instead of the split stream, and `tray.svg` is the menu bar icon (a single-colour drop with the dot cut out, used as a template image). `build/icon.png` (1024 px) and `build/icon.icns` are made from them and electron-builder reads `build/icon.icns` (`mac.icon`). In the `.icns`, the 16 px and 32 px entries use `icon-small.svg` because the split stream is not readable that small; the larger entries use `icon.svg`.

In the app, `src/app/Logo.tsx` draws the mark as an inline SVG that takes its colours from the theme tokens (`--accent` for the drop, `--on-accent` for the inside), so it follows light and dark. At 24 px and below it draws the small variant (the drop with one dot), above that the full one. It is decorative (`aria-hidden`) and carries no inline style, which the page policy forbids. The geometry lives in `src/app/logo-geometry.ts`; `test/logo-assets.test.ts` fails when an SVG in `build/` no longer matches it. The menu bar icon is `TRAY_ICON_DATA_URL` in `src/main/tray.ts` (a 32 px PNG of `tray.svg`). When the app runs unpackaged on macOS, the Dock shows `build/icon.png` (`src/main/dock-icon.ts`); a packaged app gets its icon from the bundle.

To make the PNG and `.icns` again after a change to an SVG, render each size from the SVG (sizes 16, 32, 32, 64, 128, 256, 256, 512, 512 and 1024 pixels, named as in an `.iconset` folder: `icon_16x16.png`, `icon_16x16@2x.png`, `icon_32x32.png`, `icon_32x32@2x.png`, and so on), then run `iconutil -c icns <folder>.iconset -o build/icon.icns`.

### The engine process

The main process gives the engine a random token and port 0, reads `{"type":"listening","port":...}` from its output, and tells the window the address through `window.rill.engine.info()` and the current state through `window.rill.engine.status()` (the status events only report changes, so a page that loads late asks once). It restarts the engine, gracefully (10 seconds, then kill), when the provider, model, key, allowed folders or saved connections change. A change of a Google or Microsoft account does not restart it: the main process posts the new access token to the running engine (see "Google and Microsoft sign-in"), and the engine receives its first tokens in `RILL_CONNECTIONS`. After a crash it restarts with a back-off of 1, 2, 4, 4 and 4 seconds. On the sixth failure within a minute, or the sixth failed start in a row, it shows the stopped state and waits for the user (the restart button of the window, or a settings change, starts it again). An engine that exits with the usage error code 2 is not retried. Allowed folders are the app's own attachment folder (always the first `--allow`) plus the folders the user chose; with none chosen the engine can only touch attachments. If a change of settings arrives while a restart has already read the old settings, one more restart runs after it, so a removed folder or key never stays in force.

A folder can only be added when the folder dialog returned it in this run; `settings.update` accepts removals, folders that are already allowed and picked folders, nothing else. The main process also refuses `/`, the system folders, the home folder, any folder above the data folder, the data folder itself and links that lead to them, so a workflow cannot reach `config.json` and widen its own access.

### Security settings of the window

`contextIsolation` and `sandbox` are on, `nodeIntegration`, `webviewTag` and `allowRunningInsecureContent` are off, and `webSecurity` is on. The packaged app turns the developer tools off (`devTools: false`) and installs a menu with only the app and edit menus, so there is no View menu with Toggle Developer Tools or Reload. The page is served from the custom scheme `app://rill/` (`src/main/app-protocol.ts`), which maps to the renderer folder only and refuses `..`, encoded slashes, NUL and other hosts; the page is not loaded from `file://`. The page carries a content security policy that allows only the app's own origin and `ws://127.0.0.1:*` and `ws://localhost:*` for connections. New windows and navigation away from the app page are denied, every permission request is denied, and `shell.openExternal` is not exposed. The engine refuses WebSocket requests with an `Origin` header, which the page always sends, so the main process removes that header from requests to `127.0.0.1` and `localhost` for this window only; the token is still required. The window can copy a file into the attachment folder by path only after the user picked that file in the file dialog; dropped files go through `attachments.addFromBytes`.

### Smoke mode

    apps/desktop/release/mac-arm64/Rill.app/Contents/MacOS/Rill --smoke
    pnpm --filter @rill/desktop smoke

`--smoke` starts a hidden window and the engine in a temporary data folder with its own stand-in for `safeStorage` (the real keychain is not touched), waits until the page has connected to the engine and sent `ping`, prints one JSON line such as `{"ok":true,"windowApi":true,"engine":true,"ping":true,"pingMs":2,...}`, stops the engine and exits with 0 (1 on any failure or after 45 seconds). It is the only check of the real Electron chain; the unit tests use fakes. The token and the address are never printed. It counts Content Security Policy violations twice, in the page (`cspViolations`) and as console messages that the main process saw from the start of the load (`cspConsoleMessages`), and any count other than 0 fails the run.

### Known limits

The build is signed ad hoc only. The smoke run is macOS only and was not tried on Windows or Linux. `safeStorage` on a Mac with a locked keychain can show a prompt the first time it is used. A corrupt secrets file means the user must enter the keys again, and the settings page does not tell the user that the file was unreadable yet (the contract has the code `SECRETS_UNREADABLE`, nothing sends it). A single huge `addFromBytes` call is deserialized by Electron before the main process can check its size, so the 21 MiB limit protects the disk, not the memory of that one call. The real `safeStorage` is not used by any automated check, so the first save of a key in a real run is the first time it runs. The same holds for the key check: its addresses and wording rules are from documentation and were never called live.

## Tests

    pnpm --filter @rill/desktop exec vitest run

or `pnpm test` from the root. The desktop tests use Vitest with jsdom and Testing Library, in a project of their own. React Flow needs `ResizeObserver`, `DOMMatrixReadOnly` and a few size getters, which `test/setup.ts` stubs in one place. The logic tests (layout, run state, JSON model, time) run in the node environment. The graph test also runs axe-core on a selected card with run states.

The tests of the main process, the preload and the build configuration are `test/main-*.test.ts`, `test/renderer-shell.test.tsx` and `test/main-installer-config.test.ts`. They run in the node environment with fakes for Electron, the keychain and the child process; `main-engine-bundle.test.ts` bundles the engine and starts it with plain Node. The `src/main` and `src/preload` folders are node side code, so the browser-only lint rule and the browser build checks skip them.
