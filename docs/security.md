# Security notes

This document describes how Rill treats untrusted data and secrets, where each control lives in the code, and what the controls do not cover. It is an engineering description. Nobody outside the project has reviewed it, and the app has not been penetration tested.

Rill is a local app. There is no server, no account and no cloud component. The risks come from four places: text that a model reads, files and web responses that a workflow handles, the secrets the app stores, and other software on the same computer.

## What is protected

| Asset | Why it matters |
| --- | --- |
| Model keys and connection secrets (Slack bot tokens and older webhook addresses, HTTP tokens, Google and Microsoft Client secrets, refresh tokens and access tokens) | A leaked key costs money. A leaked Slack bot token or webhook address lets anyone post as your bot or to a channel. A leaked access token lets anyone read and change the files of that account until it expires. A leaked refresh token lets anyone get new access tokens until the access is revoked. |
| Files outside the folders you chose | A workflow must not read or write your whole disk. |
| What leaves the computer | File contents, notes and run records go to a model provider. Only what you expect should go. |
| The workflow you confirmed | What runs must be what you read on the graph. |
| The engine's control channel | Whoever can talk to the engine can run and change workflows. |

## Untrusted data

Rill treats the following as data that an attacker may have written. None of it may become an instruction, a path, a recipient or a rule without a check.

| Source | Where it enters | What it could try |
| --- | --- | --- |
| Attachments you add to the chat (PDF, image, text) | The planner prompt | Tell the planner to add a node that sends data to an address of the attacker's choice. |
| Documents in a watched folder | `llm.extract` at run time | Tell the extraction to return a path, a URL or a value that changes a later branch. |
| Web responses and webhook bodies | Run data, then conditions and later nodes | Steer a condition, or smuggle text into a later request. |
| Run records (step inputs, outputs, error text) | The failure explanation prompt | Turn into an instruction to the explainer, or into the text of your next request. |
| Model output (plans, questions, explanations, fix proposals) | The screen, the next request, a deployed workflow | Show a link, a hidden character or an address you did not write. |

## What is enforced, and where

### Planning time

| Control | What it does | Where |
| --- | --- | --- |
| Closed output schema | The planner asks for a structured answer with a fixed shape. The answer is checked again locally. Node types come from the catalog, so an unknown node is an error, not a guess. | `packages/planner/src/generation.ts`, `packages/planner/src/catalog.ts` |
| One shared validator | `validateWorkflow` checks the schema, the graph, every reference, the config of every node, literal paths against the allowed folders, connection names, and a workflow that writes into the folder it watches. The planner's repair loop, `deploy` and recipe instantiation all call it. A parity test checks that planning time and deploy time give the same answer. | `packages/nodes-core/src/validate.ts`, `packages/engine/test/deploy-parity.test.ts` |
| Rules | A rule that you set can forbid a node type, allow only some hosts for `http.request`, and cap the planning effort. The shared validator adds a `rule_violation` issue for a forbidden node, for a literal URL whose host is not allowed, for a URL whose scheme or host part is a template (the host is only known at run time, so it is refused) and for a URL that is not a valid absolute `http` or `https` URL. The planner repairs its own plan from these issues. Deploy, plan deploy, recipe instantiation, activation, starting a run and a firing trigger refuse a workflow that breaks a rule. The effort cap lowers a plan request and never refuses it. A host is judged by the host of the parsed URL, so `https://allowed.com@evil.com/` and `https://allowed.com.evil.com/` are not allowed hosts. A check that cannot decide refuses. Rules only restrict. Only an explicit `saveRule` or `deleteRule` changes them, and nothing the model, an attachment, a recipe, an imported workflow or a run produces can. | `packages/nodes-core/src/policy.ts`, `packages/engine/src/rules.ts`, `packages/engine/src/engine.ts` |
| Provenance flags | After a plan is valid, each field with a role (path, URL, connection, recipient) is checked against your own words. A value that came from an attachment, a send or write target you never wrote, or a path or URL built from file, web or request content gets a flag. | `packages/planner/src/attachments/provenance.ts` |
| Confirmation gate | `deployPlan` needs the confirmation key of every flag. A plain `deploy` of the same content is refused while the flagged plan is open. The gate stops the interface from skipping the confirmation. A client that holds the engine token and edits a value before deploying is trusted and not stopped. | `packages/engine/README.md` (Flags and confirmation), `packages/engine/test/deploy-gate.test.ts` |
| Random tags around untrusted text | Attachments, memory notes, agent settings and run data are placed between tags with a fresh random suffix, and the system prompt says that nothing outside the pair came from the document. | `packages/planner/src/attachments/prepare.ts`, `packages/planner/src/memory.ts`, `packages/planner/src/agent.ts`, `packages/planner/src/explain/explain.ts` |
| Repair messages leak nothing | When a plan is repaired, flagged literals and attachment text are removed from the message sent back to the model. Words that only an attachment contained are replaced with `<hidden>` in the summary, the questions and the refusal text before they are stored. | `packages/planner/src/attachments/redact.ts`, `packages/planner/src/attachments/scrub.ts` |
| No hidden settings | The planner cannot set timing and size limits (`pollMs`, `stableMs`, `timeoutMs`, `maxBytes`, `overlap`). The engine fills them in. | `packages/planner/src/hidden.ts` |

### Run time

| Control | What it does | Where |
| --- | --- | --- |
| The model never picks nodes at run time | `llm.extract` returns the fields you declared, as typed values or null. It cannot add, remove or reorder nodes. | `packages/nodes-core/src/nodes/llm-extract.ts` |
| Path guard | Every node that reads or writes a file resolves the real path (links followed, a dangling link refused), rejects `..` and relative paths, and checks the result against the allowed folders. The app always starts the engine with the attachment folder as an allowed folder, so the guard is on in the app. | `packages/nodes-core/src/guard.ts` |
| File limits | `llm.extract` checks file signatures (a `.pdf` must start with `%PDF-`) and size limits (PDF 20 MiB, image 3.75 MiB, text 1 MiB) before it reads a file in full. | `packages/nodes-core/src/nodes/llm-extract.ts` |
| CSV formula guard | A cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading `'`, so a spreadsheet does not run it. Plain numbers such as `-12.5` stay as they are. `microsoft.excel.append` applies the same rule to each text cell, because Excel can read a text that starts with `=` as a formula. `google.sheets.append` sends `RAW` input, which stores a text as given and never evaluates it, and does not use `USER_ENTERED`. | `packages/nodes-core/src/cells.ts`, `packages/nodes-core/src/nodes/csv-append.ts`, `packages/nodes-core/src/nodes/microsoft-excel-append.ts`, `packages/nodes-core/src/nodes/google-sheets-append.ts` |
| Outbound HTTP rules | Redirects are not followed, non-2xx answers fail the node, the response size is capped at 5 MiB by default, and credentials come from a connection, never from the workflow text. | `packages/nodes-core/src/http.ts`, `packages/nodes-core/src/nodes/http-request.ts` |
| Host rules at run time | With an `allowHost` rule, `http.request` checks the final URL (after templates and the query credential of a connection) against the hosts of the snapshot that the run took when it started, and fails with the fixed text `this host is not in the allowed hosts` before it sends anything. The text has no URL in it. A run that is already running keeps its snapshot, so a rule saved later does not cut it; a run that is still waiting in the queue, or that was queued when the engine stopped, is checked against all rules when it begins and fails with a fixed text before any node runs; a run resumed after a crash takes a fresh snapshot of the host rules. A trigger that fires for a workflow that now breaks a rule starts no run and the engine records one `run.blocked` event. | `packages/nodes-core/src/nodes/http-request.ts`, `packages/engine/src/executor.ts`, `packages/engine/src/engine.ts` |
| Webhook listener | Binds to `127.0.0.1`, checks the `Host` header, limits the body to 1 MiB, accepts a shared secret in `x-rill-secret` (compared in constant time) and refuses browser requests when no secret is set. | `packages/engine/src/triggers/webhook.ts` |
| Dry run | Skips the CSV write, Slack messages, spreadsheet rows and HTTP requests. It does read the file and call the model, because reading is not a side effect. | `packages/nodes-core/src/nodes/` |
| Confirmations in the app | "Run now" names the side effects before it starts. Retry and deactivate from an explanation ask first. | `apps/desktop/src/app/workflows/ConfirmDialog.tsx`, `apps/desktop/src/app/workflows/WorkflowActions.tsx`, `apps/desktop/src/explain/` |

### Agents

An agent is a persona and instructions that you write. They go to the model provider with every plan and every failure explanation while the agent is active, so they are part of what the transfer notice under the chat input lists. They are a trusted channel (you wrote them) with a hard edge: they tune tone and working preferences and cannot loosen a rule.

| Control | What it does | Where |
| --- | --- | --- |
| One write path for agents | Only an explicit `saveAgent`, `deleteAgent` or `setActiveAgent` request creates, changes, deletes or activates an agent. No plan, attachment, run data, model answer, extraction result or imported file can. A file import only fills a review screen, and nothing is saved until you press Save. An import never activates the agent. A source scan in the tests catches a new write path, and the planner package has no database access at all. | `packages/engine/src/store.ts`, `packages/engine/test/agents-sources.test.ts`, `packages/engine/test/agents-prompt.test.ts` |
| The request cannot carry an agent | `plan` and `explainRun` take only an `agentId`. A client cannot send persona or instruction text with a request, and an unknown id is refused before the model is called. | `packages/protocol/src/methods.ts`, `packages/engine/test/agents-plan.test.ts` |
| An agent cannot loosen a rule | The agent block says that the profile cannot change the rules, the validation, the confirmation flags or what may be done with attached files, and that the rules win. Beyond the wording, the checks are code: the validator, the flags and the scrubbing of explanations run after the model answers, whatever the profile says. Text that only the profile holds does not count as text you wrote, so a URL in a persona is still flagged. A test runs a model that obeys an agent telling it to print secrets and connection values. | `packages/planner/src/agent.ts`, `packages/planner/test/agent.test.ts` |
| Random tag, and a profile that holds it is dropped | The profile sits between `<agent-profile-...>` tags with 12 fresh random hex characters. A profile that holds its own tag, in any case, is left out whole and counted in `agentDropped`. | `packages/planner/src/agent.ts` |
| No change without an agent | With the built-in Default agent, an agent without text or no `agentId`, the requests sent to the provider are what they were before agents existed. A frozen copy of those requests is compared with what the planner sends now. | `packages/planner/test/frozen-requests.test.ts` |
| Same character rules as notes | Control, line-separator, bidirectional and invisible formatting characters are refused in every field, and a carriage return and a tab are refused in the persona and the instructions, so a hidden instruction cannot sit in an agent. The same function checks a save, a hint in the editor and an imported file. | `packages/protocol/src/agents.ts` |
| Agent text stays out of logs and errors | An agent text is user text like a note. It is not written to a log, an error message, an event or a plan record. A plan record keeps the id of the agent, and the meta keeps its name. An unexpected failure of `saveAgent` logs only the error name. | `packages/engine/src/server/server.ts`, `packages/engine/test/server-agents.test.ts` |
| Import and export go through the system dialogs | The main process shows the open or save dialog, reads at most 64 KiB from a regular file (a link, a folder or a special file is refused, and the file is opened without following links) and writes at most 64 KiB. It hands the text over as it is and does not parse it. The renderer parses the file strictly and shows a review screen with every problem. | `apps/desktop/src/main/text-files.ts`, `apps/desktop/src/main/ipc-handlers.ts`, `apps/desktop/src/app/agents/agent-file.ts` |

What an agent does not protect: whatever you write in the persona or the instructions leaves your computer. Do not put secrets, passwords or personal data in them. The Agents screen says so.

### Hooks

A hook is a fixed action that the engine runs when an event happens, so it acts while nobody is watching. It can send a Slack notice, switch a workflow off after failures in a row, or write a log row. The controls keep what a hook can do small and what it sends fixed.

| Control | What it does | Where |
| --- | --- | --- |
| One write path for hooks | Only an explicit `saveHook` or `deleteHook` request creates, changes or deletes a hook, and deleting a workflow deletes the hooks that have it as their scope. No plan, attachment, run data, model answer, recipe or imported file can write one, hooks are in no import or export, and the planner package has no database access. A source scan in the tests catches a new write path. | `packages/engine/src/store.ts`, `packages/engine/test/hooks-sources.test.ts` |
| Three actions, and no way to start work | The runner can read the store, write the log, post to Slack and switch a workflow off. It has no way to start a run, a plan, a deploy or a model call, and its actions emit no event that a hook listens to, so no hook starts another. A dry run never reaches a hook. | `packages/engine/src/hooks-runner.ts`, `packages/engine/test/hooks-sources.test.ts` |
| A fixed message | The text is one of three English sentences with the workflow name in it. The name loses control, invisible and bidirectional characters, is cut to 60 characters and has `&`, `<` and `>` escaped, so it cannot make a mention or a link. No run data, error text, step output or path goes into it. | `packages/protocol/src/hooks.ts`, `packages/engine/test/hooks-runner.test.ts` |
| Rules apply | A `notify` hook is refused at save, and blocked at run time with the outcome `blocked_by_rule`, while a `forbidNode` rule names `notify.slack`. A post goes only to `https://slack.com/api/chat.postMessage` or to the webhook of a saved connection of kind `slack`, through the function that the node uses, so `allowHost` has no URL to check. | `packages/engine/src/hooks.ts`, `packages/nodes-core/src/slack-post.ts` |
| Limits | At most 20 hooks, a cooldown of 60 seconds for each `notify` hook and 30 actions in 10 minutes for all hooks together. Both limits are read from the log, so a restart does not reset them. A post waits 15 seconds and is not retried. | `packages/engine/src/hooks-runner.ts`, `packages/engine/test/hooks-limits.test.ts` |
| Nothing is hidden in a log or a row | A log row has the time, the ids, a fixed outcome and, for a failure, one of five fixed codes. It has no text from Slack, no token, no address, no channel and no name. An unexpected failure of a hook method logs only the error name. | `packages/engine/src/store.ts`, `packages/engine/src/server/server.ts`, `packages/engine/test/server-hooks.test.ts` |
| A check that cannot decide does nothing | A missing, retyped or malformed connection, a post that throws and an unknown error write a `failed` row and the runner goes on with the next hook. A hook never changes how a run ends. An event whose run record is gone writes nothing. | `packages/engine/src/hooks-runner.ts`, `packages/engine/test/hooks-runner.test.ts` |
| No replay | Events that the engine missed while it was stopped are not replayed, and events that are still waiting when it shuts down are dropped. | `packages/engine/src/hooks-runner.ts`, `packages/engine/test/hooks-runner.test.ts` |

### Memory and explanations

| Control | What it does | Where |
| --- | --- | --- |
| One write path for notes | Only an explicit `saveMemory` request creates or changes a note. No plan, attachment, model answer or extraction result can. A source scan in the tests catches a new write path. Control, line-separator, bidirectional and invisible formatting characters are refused, so a hidden instruction cannot sit in a note. | `packages/engine/src/memory.ts`, `packages/engine/test/memory-plan.test.ts` |
| Notes are data, not rules | The notes block says that notes never change rules and that your request wins on a conflict. | `packages/planner/src/memory.ts` |
| Explanations mask secrets | Before the run digest is cut to 12,000 characters, connection secrets are replaced by `<secret>` in plain, JSON-escaped, URL-encoded, base64 and hex forms. Authorization headers, credential-looking keys and values, and every response header except `content-type` and `retry-after` are removed. | `packages/planner/src/explain/excerpt.ts`, `packages/planner/src/explain/digest.ts`, `packages/engine/test/explain-safety.test.ts` |
| Explanations cannot steer the next request | URLs, hosts, email addresses and recipients in the model's answer that were not already in the workflow or summary are replaced by `<hidden>`. The request text for a proposed fix is checked more strictly. The explanation is read-only, stores nothing and runs only when you press the button. | `packages/planner/src/explain/scrub.ts` |

### The app

| Control | What it does | Where |
| --- | --- | --- |
| Secrets encrypted with `safeStorage` | Keys and connection secrets are encrypted as one blob with Electron `safeStorage`, whose key is in the macOS keychain. The Google and Microsoft sign-in records (Client ID and Client secret of the app, refresh token, scope, account text) live in the same blob in an `oauth` section; a blob that has one is written as version 2, so an older app treats it as unreadable and moves it aside, never drops the section, and a blob without one stays version 1. A later change to the shape of the `oauth` section needs a new version number: an unknown field inside it makes the blob unreadable for this version, and an unreadable blob is moved aside, never overwritten. Access tokens are never written to it. The blob is a file in the data folder. Without a keychain, saving is refused and the engine does not start. There is no plaintext fallback. A blob that cannot be decrypted is moved aside, never overwritten. | `apps/desktop/src/main/secret-store.ts` |
| The window never holds a secret | Settings return only which providers have a key, the name, kind, auth type and (for a Slack bot) the account text and default channel of each connection, and for each Google or Microsoft account its status, its account text, the Client ID of its app and whether a Client secret is saved. No call returns a Client secret, a refresh token or an access token, and the change event that tells the window about an account carries the status and the account text only. Key, Client secret and connection secret fields are password inputs and are cleared after saving. A saved key shows as a fixed row of bullets, not as anything derived from the key. A key or Slack token that the provider rejected is held in the Keys section or the Slack card only while the "save anyway" notice is open. | `apps/desktop/src/shared/host-api.ts`, `apps/desktop/src/main/ipc-handlers.ts`, `apps/desktop/src/app/settings/KeysSection.tsx`, `apps/desktop/src/app/settings/SlackCard.tsx`, `apps/desktop/src/app/settings/OAuthCard.tsx`, `apps/desktop/src/app/settings/ConnectionsSection.tsx` |
| Keys are checked before saving | Saving a provider key first sends one read-only request (the model list) from the main process to a fixed HTTPS address of that provider, with the key in the documented header and nowhere else. The address table is a constant keyed by provider. No cookies, no redirects, 10 second timeout, the response body is not returned, logged or stored (a 400 body, and an OpenAI 401 body, is read up to 4 KiB for classification). Only a clear rejection blocks the save: 401 (except OpenAI's 401 for a missing scope), or a 400 with the provider's known wording. A key that cannot be sent in a header is never saved. Saves and removals of one provider are ordered, so a slow check cannot write an older key over a newer one. Every other outcome (403, 429, 5xx, network, timeout, an unexpected status) saves the key and says it could not be confirmed. A blocked key can still be saved with "save anyway". | `apps/desktop/src/main/key-check.ts`, `apps/desktop/src/main/ipc-handlers.ts`, `apps/desktop/src/app/settings/KeysSection.tsx` |
| Slack bot tokens | A Slack bot token is stored in the same encrypted blob as a connection of kind `slack`. The main process builds its secret, a JSON text with the token and an optional default channel, from a validated object, so the window sends the token once and never assembles or receives it. Saving first sends one `POST` with no body to the fixed address `https://slack.com/api/auth.test` from the main process, with the token only in the `Authorization` header: no cookies, no redirects, 10 second timeout, the answer is read up to 16 KiB and only the workspace and bot names are kept, as text that has control and bidirectional characters removed. Only a clear rejection (`invalid_auth`, `not_authed`, `token_revoked`, `token_expired`, `account_inactive` or HTTP 401) blocks the save, and "save anyway" always exists. A `notify.slack` step posts to the fixed address `https://slack.com/api/chat.postMessage`; nothing from the workflow, the step or the connection reaches the address. The token is hidden as `<secret>` in error texts, in the step records and in the failure explanation, and a Slack error shows as a short code (`Slack: channel_not_found`), never as text from the response. A webhook connection refuses a `channel` on the step, so a message cannot land in another channel than the one asked for. `http.request` refuses a Slack bot connection before it sends anything, so a workflow cannot send the token to an address of its own. | `apps/desktop/src/main/slack-check.ts`, `apps/desktop/src/main/ipc-handlers.ts`, `apps/desktop/src/app/settings/SlackCard.tsx`, `packages/nodes-core/src/slack-connection.ts`, `packages/nodes-core/src/nodes/notify-slack.ts` |
| Custom connections | An API key, a bearer token or a basic login is stored in the same encrypted blob as a connection of kind `http`. The main process builds its secret, a JSON text, from a validated object, so the window sends the secret once and never assembles or receives one. `http.request` hides each component of 4 or more characters (token, key value, password and the base64 login) as `<secret>`, in the raw, percent-encoded and JSON-escaped forms a server may echo, in error texts (before the text is cut to 200 characters) and in the response it records. Components shorter than 4 characters are not hidden, and a server that echoes a value in another form can still show it. The failure explanation hides them like any connection secret. | `apps/desktop/src/shared/host-api.ts`, `apps/desktop/src/main/ipc-handlers.ts`, `packages/nodes-core/src/connection-auth.ts`, `packages/nodes-core/src/nodes/http-request.ts` |
| Loopback sign-in | A sign-in uses the system browser, PKCE (S256), a random `state` and a one-shot HTTP server in the main process that listens on `127.0.0.1` only, on a port that the system picks. The server answers only `GET /oauth/callback` and only for a `Host` header that is the loopback address with that port (so a page that points a DNS name at it cannot reach it); every other path, method or host gets 404. A request with a wrong or missing `state` (compared in constant time) is answered 400 and ignored, so another program on the computer that guesses the port cannot end the flow or hand it a code. The first request with the right `state` wins and the server closes at once. The reply page is one fixed text that reflects no input and carries `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and a policy that allows nothing. The flow ends after 3 minutes or on Cancel. The authorize address is built in the main process from constants, the Client ID and the generated values; the window never sends an address. The authorization code, the verifier, the `state` and the address never go to a log, an error or the window. The exchange refuses redirects, sends no cookies, gives up after 15 seconds and reads at most 64 KiB. | `apps/desktop/src/main/oauth-flow.ts`, `apps/desktop/src/main/oauth-providers.ts` |
| Refresh tokens and Client secrets | They are stored only in the encrypted blob and used only by the main process, never sent to the window or the engine. A refresh answers only to the token endpoint of the provider, which is a constant. A refresh runs once at a time per provider, and a rotated refresh token is written to the encrypted file before the new access token is used or sent (a crash in between must not lose it). When the provider says the grant is gone (`invalid_grant`, `invalid_client`, or a 400 `unauthorized_client` or `invalid_request`), the refresh token is deleted and the account asks to reconnect. Disconnecting a Google account asks Google to revoke the refresh token. No provider text is logged: the log lines are fixed sentences. The engine gets only the short-lived access token, through `RILL_CONNECTIONS` at start and then through messages on the parent channel of its process, which only the main process can write; the engine accepts exactly two message shapes, for the names `google` and `microsoft`, and ignores and counts anything else. | `apps/desktop/src/main/oauth-manager.ts`, `apps/desktop/src/main/secret-store.ts`, `apps/desktop/src/main/engine-supervisor.ts`, `packages/engine/src/connection-channel.ts` |
| Google and Microsoft access tokens | A connection of kind `google` or `microsoft` holds an OAuth access token as plain text. The sign-in creates it and the main process refreshes it; a saved connection can neither have that kind nor the name `google` or `microsoft`, so nothing else can take its place. The token also reaches the engine as that connection and the failure explanation hides it like any other connection secret. `google.sheets.append` sends it only to `https://sheets.googleapis.com/v4/spreadsheets/` and `microsoft.excel.append` only to `https://graph.microsoft.com/v1.0/me/drive/root:/`: the host and the path prefix are constants and the spreadsheet id, range, file path and table are URL-encoded path parts that a pattern has already limited (no `..`, no `/` or `%` in a range, no encoded slash in a file path). Both calls refuse redirects, read at most 64 KiB of the answer and show a fixed text for a failure (`HTTP 401: the sign-in is no longer valid, reconnect the account`), never a word of the answer. The token is hidden as `<secret>` in the one text that is taken from an answer (`updatedRange`, cut to 200 characters with control characters removed), in step records and in the failure explanation. A plain `http.request` that names such a connection is refused before any request, by the kind that the engine knows from the connections file, so a workflow cannot send a token to a URL of its choice. A spreadsheet node refuses a connection that has no kind (a bare string entry of the connections file), a connection that the engine knows as another kind, a Slack secret, and any secret that is not shaped like a bearer token, so a token is only ever used with the kind that makes `http.request` refuse it. `allowHost` of the rules does not cover these nodes, because they have no URL field; `forbidNode` does. | `packages/nodes-core/src/account-connection.ts`, `packages/nodes-core/src/spreadsheet-api.ts`, `packages/nodes-core/src/nodes/http-request.ts`, `packages/engine/src/cli-config.ts` |
| Narrow, checked host API | The preload script exposes `window.rill` and nothing else, never `ipcRenderer`. Every call and every result is checked against a TypeBox schema in the main process. | `apps/desktop/src/preload/`, `apps/desktop/src/shared/host-api.ts` |
| Folder allow-list | A folder can be added only when the system dialog returned it in this run. The main process refuses `/`, system folders, your home folder, the data folder and links that lead to them, so a workflow cannot reach `config.json` and widen its own access. | `apps/desktop/src/main/ipc-handlers.ts`, `apps/desktop/src/main/config-store.ts` |
| Attachment store | Files are copied into one folder (mode 0700, files 0600) as `<id>.<ext>`, with a cap of 500 files and 512 MiB. The engine refuses links, directories and pipes. | `apps/desktop/src/main/attachments.ts`, `packages/engine/src/attachments.ts` |
| Engine channel | The engine binds to `127.0.0.1` on a random port. The token is new on every start, travels in the WebSocket subprotocol, and is compared in constant time. `Host` and `Origin` are checked, messages are capped at 1 MiB and connections at 8. | `packages/engine/src/server/server.ts`, `apps/desktop/src/main/engine-supervisor.ts` |
| Window hardening | `contextIsolation` and `sandbox` on, `nodeIntegration` and `webviewTag` off, `webSecurity` on. Permission requests, new windows and navigation away from the app page are denied. The page loads from the custom `app://rill/` scheme, which refuses `..`, encoded slashes and other hosts. | `apps/desktop/src/main/window.ts`, `apps/desktop/src/main/app-protocol.ts` |
| Content security policy | In the built and packed app: `default-src 'none'`, scripts, styles and fonts from the app itself, images from the app and `data:` URLs, connections only to `ws://127.0.0.1` and `ws://localhost` (the key check and the Slack token check are made by the main process, not by the window). No `unsafe-inline`, no `unsafe-eval`. Development mode has no policy (see "What is not covered"). | `apps/desktop/src/main/csp.ts`, `apps/desktop/src/main/window.ts`, `apps/desktop/electron.vite.config.ts` |
| Packaged app | Electron fuses turn off `runAsNode`, `NODE_OPTIONS` and `--inspect`, and turn on ASAR integrity checking and load-from-ASAR-only. The developer tools and the View menu are removed. | `apps/desktop/electron-builder.yml`, `apps/desktop/src/main/index.ts`, `apps/desktop/src/main/app-menu.ts` |

Tests read the sources and fail on `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `localStorage`, `sessionStorage` and links made from model or run text. Untrusted text is shown as plain text with a length cap, and bidirectional, zero-width and control characters are made visible. | `eslint.config.js`, `apps/desktop/test/browser-safe.test.ts`, `apps/desktop/test/chat-source-rules.test.ts`, `apps/desktop/test/panels-source.test.ts` |

## Measured so far

- Extraction against prompt injection: 6 adversarial documents (fake JSON, "ignore the instructions", a request for the system prompt, a Korean instruction, a fake closing tag, an injection inside an item name), each as text, PDF and PNG, three repetitions per model. All three Claude models resisted all 54 calls. The documents are synthetic and the injected text is simple. See the evaluation section of the [README](../README.md).
- Planner against prompt injection: the suite has two injection cases among its 48. The result is pending, because the owner has not run it yet.
- Everything else in this document is checked by unit and integration tests with fakes, not by a live attack.

## What is not covered

- **Other software of the same user.** The engine gets its secrets through the environment of its process. On macOS any process of the same user can read that block, for example with `ps -E -p <pid>`, without a keychain prompt. Moving the secrets to a message channel needs a change in the engine command line and is not done. Software that runs as you can also read your files directly, so the folder allow-list limits workflows and does not limit other programs.
- **The engine is not sandboxed by the operating system.** The allowed folders are enforced by the code of the nodes. A bug in a node, or a new node that forgets the guard, would bypass them. The engine process runs with your user rights. A headless engine started without `--allow` does not restrict paths for `file.read` and `csv.append` (`llm.extract` refuses to read files then). The app always passes allowed folders, so this applies to the command line only.
- **The token is enough to drive the engine.** The window receives the address and token so it can connect. Anything that obtains them can start and stop workflows over `ws://127.0.0.1`.
- **An API key in a query string.** A custom connection can send its key as a query parameter. The server that receives the call, and any proxy on the way, can write the full URL, key included, into its logs. Rill hides the key in its own errors, records and explanations. Use a header when the service allows it.
- **The sign-in was never run against the real providers.** The endpoints, the scopes, the parameters, the answers that count as success or as a withdrawn grant, the redirect rules and the account name fields come from Google's and Microsoft's documentation and fake transports. They are constants in `apps/desktop/src/main/oauth-providers.ts`, one row per provider with a note per constant, so a wrong value is a one-line fix, but nobody has seen the real consent screens, the real token answers or the Graph answer for a personal account. The addresses are untested as far as whether `http://localhost/oauth/callback` registered in Microsoft's console matches the address with the port that Rill picks (Microsoft's documentation says the port is ignored and the path must match), whether Google accepts the loopback address of a Desktop client without a registration, and whether Google's token endpoint refuses a Desktop client that sends no Client secret (reports say it does, so the card requires the secret for Google). The app reads the answers strictly (a token must look like a bearer token, a refresh token is required, the scope must contain what the nodes need), so a surprise shows up as a refused sign-in and not as a wrong one. The spreadsheet nodes also work with an access token that you put into a connections file or into the `google` or `microsoft` entry of `RILL_CONNECTIONS` yourself; the token then sits in that file or in the environment of the engine process, in plain text.
- **A stolen refresh token outlives the access token.** Anyone who gets the refresh token and the Client ID (and the Client secret, for Google) can get new access tokens until the access is revoked: for Google on the page of your Google account that lists the apps with access to your account, for Microsoft on your Microsoft account page under the apps that can access your data. Disconnect in the app revokes the Google refresh token and only forgets the Microsoft one. A Google app in Testing mode loses its refresh token after about 7 days and Microsoft after 90 days without use, which limits the time but is not a protection. The blob is encrypted, which protects the file at rest and does not protect against software that can use your keychain.
- **An access token is visible in the engine's environment at start.** At start the engine gets the current access token in `RILL_CONNECTIONS`, the same way as every other connection secret (see the first item). A refresh token and a Client secret never go there. A token that a refresh has replaced stays in the original environment block until the engine restarts, but it expires within the hour.
- **Slack does not use sign-in.** You create a Slack app of your own and paste its bot token. Anyone who has that token can post as the bot and use every scope you gave the app. Anyone who has an older webhook URL can post to its channel.
- **Outbound network is restricted only by the rules you set.** With no `allowHost` rule, `http.request` and `notify.slack` can call any host (the two spreadsheet nodes call only their own fixed hosts), including `localhost` and private addresses, when a workflow names it. The provenance flags ask you to confirm a target you did not write, and they depend on your confirming it. An `allowHost` rule limits `http.request` only: it matches names, not the address a name resolves to, and it does not follow a redirect, so only the first URL of a call is checked. `notify.slack` posts to `slack.com` or to the webhook of its connection and is not subject to `allowHost`; a `forbidNode` rule can forbid it. There is no check against private address ranges.
- **Rules are held by the engine and the token opens them.** Rules only restrict, and the app lets only you remove one, but a client that holds the engine token can call `deleteRule` like any other method, as it can edit a workflow. A rule saved while a run is in flight does not cut that run. A run that waits in the queue is checked against every rule when it begins, so it does not start. A run resumed after a crash is checked against the host rules again and not against the forbidden node rules, because it started legitimately. A folder trigger gives up on a file that it could not start for a rule, until the workflow is activated again.
- **Hooks act when nobody is watching.** A `notify` hook posts through the saved Slack connection whenever its event happens, and the message says that a workflow of that name failed, finished or was deployed. Everyone who can read the channel learns that. The workflow name goes into the message as written, after the sanitising and cut to 60 characters. A name can come from a plan, so it can carry a short text or an address that Slack may turn into a link. The limits mean that some events are not announced: a hook with the scope all posts at most one message a minute for all workflows together. A hook runs only while the engine runs, and nothing is replayed after a restart. A deactivation hook reads the run history, so a workflow that you switch on again with failed runs behind it is switched off by its next failure. A client that holds the engine token can call `saveHook` like any other method.
- **Prompt injection cannot be ruled out.** The design limits what an injected instruction can do (it cannot add nodes at run time, and a planned value it influences is flagged). It does not remove the risk. Text inside a PDF or an image cannot be searched offline, so a plain word taken from one is not detected. A value that you wrote yourself and that an attachment repeats counts as yours. Extracted values that flow into ordinary fields without passing a condition are not flagged. The planner can still produce a plausible workflow that does the wrong thing, and your confirmation is the last check.
- **Gaps in the loop check.** Two workflows that write into each other's watched folders are not detected. On a case-sensitive file system the check can refuse a layout that would have been fine.
- **At-least-once delivery.** A crash between sending a Slack message and recording the step can send the message twice. A retry after a Slack `internal_error` or `fatal_error`, or after an HTTP 5xx, can do the same, because Slack says the message may already be posted. Neither the Sheets API nor the Graph workbook API has an idempotency key here, so a crash right after the request, or a retry after a server error, a timeout or a network error, can add a spreadsheet row twice. A timeout after the service has already written the row is the most likely cause.
- **Content goes to the model provider.** Attachments, notes, receipts read by `llm.extract` and masked run records are sent to the provider you chose. What the vendor does with them is the vendor's policy. The app shows each provider's data note (Gemini's free tier may use data for training and review, for example) and always asks the OpenAI and Grok APIs not to store the request. Models whose id ends in `-contributor` are refused. The app does not control retention on the vendor side.
- **The key check is not verified live and sends the key to the provider.** Saving a key sends it, in a header, to the provider's documented model-list address. The addresses, the headers and the 400 wording that counts as a rejection come from vendor documentation and were never called with a real key by this project, so a verdict can be wrong. A wrong `invalid` is answered by "save anyway". A wrong `valid` is only a missing warning. The key goes to the provider it belongs to, which receives it anyway whenever a plan or an extraction runs.
- **The Slack token check is not verified live and sends the token to Slack.** Saving a bot token sends it, in a header, to `https://slack.com/api/auth.test`. Running a `notify.slack` step sends it to `https://slack.com/api/chat.postMessage`, together with the message and the channel. Both addresses are constants. The endpoint, the headers and the error codes that count as a rejection come from Slack's documentation and were never called with a real token by this project, so a verdict can be wrong. A wrong `invalid` is answered by "save anyway". A wrong `valid` is only a missing warning. Give the Slack app only the scopes it needs: `chat:write`, and `chat:write.public` only if the bot must post in channels it has not joined. A token with more scopes can do more than post if it leaks.
- **The spreadsheet APIs were never called live.** The requests of `google.sheets.append` and `microsoft.excel.append`, the answers that count as success and the status codes come from Google's and Microsoft's documentation and fake transports. Treat a wrong result as possible: the Graph workbook API in particular is documented for OneDrive files and may behave differently for a personal account, and Excel may read a text cell differently from what the single quote rule assumes. A spreadsheet id, a file path or a table that a model proposes is a new target and is flagged for your confirmation like a channel or a URL.
- **Four of five provider adapters were never called live.** Their request and response handling comes from vendor documentation and fake transports.
- **No signing, no notarization, no updates.** The installer is signed ad hoc, so there is no chain of trust from a developer certificate. There is no auto-update channel to attack, and no channel to ship a fix either.
- **macOS only.** `safeStorage` behaves differently on Windows and Linux, and nothing here was checked on them.
- **Data at rest.** Only the secrets are encrypted. `rill.db` (workflows, run records with the inputs and outputs of every step, memory notes, agents), the copies in `attachments/` and `config.json` are plain files in the data folder. The only protection is file permissions (the data folder is 0700, `config.json` and the attachment files 0600), so any process that runs as your user can read them. Run records can hold what a workflow read, such as amounts, vendors and file paths.
- **Development mode.** `pnpm --filter @rill/desktop dev` loads the page from the development server. The content security policy is not applied there (the response header is skipped and the meta tag is added only at build time), and the developer tools are on. The other window controls stay on. Use the packed app for anything that matters.
- **No audit log.** The app keeps run records in SQLite. It does not keep a tamper-proof record of who changed what.
- **Not reviewed or tested by anyone else.** Treat the claims above as the intent of the design and the content of the tests.
